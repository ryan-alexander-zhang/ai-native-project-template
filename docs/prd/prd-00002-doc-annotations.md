# 文内标注 PRD

## 一句话概述

在白板编辑器的编辑与预览两种视图态里，文档负责人选中一段文本即可就地加一条
标注——question（要回答）或 issue（要修改）——攒一批统一提交给 agent，逐条
追踪回答与修改的进展。

## 愿景与目标

读文档时的反馈是带位置的，但白板现有通路接不住位置：答疑只能整篇提问、位置
靠散文转述；改进诉求更是只有「自己开修订轮当操作员」一条路；多个反馈点只能
逐条即时发起，阅读被打断或反馈被吞掉。标注把这三个缺口补上：

- 反馈自带精确位置：agent 拿到的是选区原文及上下文，不再是二手转述。
- 阅读与反馈处理解耦：读完一篇攒下的所有点一键提交，阅读全程不被打断。
- 发现问题的人只负责指出问题：issue 从「发现」到「修订轮跑完」由白板与
  agent 承担，人只在评审动作和连带确认处出手。

## 角色

- **文档负责人**（唯一人类角色）：阅读时加标注、改删未提交标注、统一提交、
  查看进展、确认连带修改请求、对修订结果照旧行使评审动作。
- **agent**（本地 CLI）：question 以 headless 只读作答；issue 由一个修订
  会话逐条修订目标文档。

## 范围

### In scope（MVP）

- 编辑与预览两种视图态下的选区标注：右键添加，类型恰为 question 与 issue。
- 一份文档多条未提交标注的暂存、修改与删除，重启不丢。
- 一键统一提交：提交时逐条校验选区锚，孤儿标注单条拦下。
- question 接入既有答疑机制，issue 触发既有修订轮。
- 标注列表：逐条类型、状态与进展（回答内容 / 修改进展）。
- 标注与进展落盘板外（`.whiteboard/`），不入 git。

### Out of scope

- comment 类型（idea 阶段已裁：值得动文档就是 issue，不值得不进系统）。
- 编辑期间的实时重锚（锚校验只在提交时做，成本裁决见 idea 已定方向 9）。
- 为标注新增编辑锁（沿用「不锁编辑」的既有取向，冲突靠既有机制）。
- `resolved`/`archived` 文档上的 issue（入口即守门，只留 question）。
- 多人协作语义（本地单人形态，同 `idea-00001` 已定方向）。
- `docs/` 之外文件的标注（白板本就不编辑 `docs/` 之外的文件）。

## 功能需求

1. **选区标注入口**：编辑与预览两种视图态下，选中文本 → 右键 → 选类型、
   填标注内容。issue 入口只对能合法转回 `draft`（或本就在 `draft`/`open`）
   的文档开放；`resolved`/`archived` 的文档只有 question 可选——不让人攒
   注定提交不了的标注。
2. **选区锚**：标注锚定选区文本及其上下文，不锚行号；文档其余部分怎么改，
   锚都不受影响。标注同时携带选区原文引用，作为锚失效后的兜底。预览里的
   选区同样要落到源文本上的锚（实现属 design）。
3. **未提交标注的暂存**：一份文档可攒多条未提交标注，提交前可改可删；
   暂存落盘板外，白板重启、页面刷新不丢。
4. **统一提交**：一个按钮提交该文档全部未提交标注。提交那一刻逐条重新
   定位锚：定位不到的标为孤儿标注、单条拦下（留在未提交区、标明失效，
   待重新选区或删除），其余照常提交——一条失效不卡整批。
5. **question 走答疑**：每条 question 按既有答疑语义开一条答疑线程，
   headless 只读作答，不改文件、不产生 commit、不占终端形态会话名额；
   与手打的答疑问题唯一的差别是问题自带选区原文与上下文。
6. **issue 走修订轮 + 共写**：同次提交的全部 issue 作为材料合入一个
   **共写会话**（复用既有共写能力，不新立会话种类）：目标文档经合法
   状态流转转回 `draft`，会话按 issue 逐条修订正文，共写的写域保证只动
   目标文档；之后审计、接收照既有语义走，共写不是评审动作、不替人接收。
   目标文档已有运行中终端形态会话（含标注自己发起的共写会话）时，提交
   按既有同文档互斥被拒、原因指明互斥；被拒的标注留在未提交区，会话
   结束后再点一次即可——不引入排队机制。提交前文档须无未保存改动，
   有则拒绝并提示先保存——不让人提交注定成孤儿的标注。
7. **含糊与连带都停下来问**：会话不替人拿主意。发现某条 issue 需要连带
   修改关系文档时，停下来（既有等待输入机制）向负责人报告——连带修改
   不在本会话落地（共写写域使然），由人对关系文档另行处理；遇到写得
   含糊、意图拿不准的 issue，同样停下来确认意图后再改（收敛纪律的细化
   属 spec）。
8. **标注列表与进展**：一份文档的全部标注逐条可见类型与状态——question 呈
   回答内容，issue 呈处理进展与所做修改。提交后锚失效（比如修订把别条的
   锚文本改了）不算标注失效：呈现以原文引用兜底，定位退化为「原文已变更」
   提示，不中断处理。
9. **落盘与留痕**：标注本身与逐条进展落 `.whiteboard/`，与答疑线程同口径，
   不入 git；issue 引发的文档修改靠修订会话既有的 commit 留痕。

## 用户体验期望

- 加标注不打断阅读：选中、右键、填完即回到原处，无页面跳转。
- 未提交标注在文档内可见（选区有痕迹可寻），一览处可看全部待提交条目。
- 孤儿标注被拦下时，明确指出是哪条、原选区原文是什么，改锚或删除一步可达。
- 提交后进展一眼可辨：哪条已回答、哪条修订中、哪条已完成。
- 「原文已变更」的退化提示要可辨识，但不打扰——它不是错误。

## 风险与依赖

- **依赖**：答疑机制（`spec-00005`）、共写（`spec-00006`，issue 通路的
  承载）、修订轮与状态流转（`rule-00001`）、会话并发与同文档互斥
  （`spec-00003`）、等待输入与桌面通知（`spec-00003`/`spec-00004`）、
  编辑器与预览（`spec-00001`）。
- **预览选区映射**：预览渲染文本与 Markdown 源不一一对应，选区→源锚的
  映射是 design 必解题；解不好则双模式退化为单模式，产品价值折损最大的
  一块在阅读主场景（预览）上。
- **共写批处理的质量**：一个会话逐条处理多条 issue，前面的修改可能影响
  后面条目的上下文；原文引用兜底缓解定位问题，但语义冲突（两条 issue
  对同一段提相反要求）只能靠会话判断与等待输入上抛。
- **板外状态与文档漂移**：标注落盘板外、文档在 git 里演进，长期积累的已
  完成标注对早已面目全非的文档还有多少意义——需要设计上限或清理口径，
  属 spec/design 权衡。
