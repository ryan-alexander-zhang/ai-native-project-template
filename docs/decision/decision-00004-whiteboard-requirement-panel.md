# Decision: 需求条目读在检视面板与子画布，不读在顶层图上

> 文档内部的正式编号条目（spec 的 FR、rule 的 BR 及各自的 AC）与 record 的验收行
> 要在白板上可见。处置是**检视面板为主、子画布为辅**：条目在选中节点的侧边面板里
> 读，验收链路下钻进子画布看；条目**不成为顶层图的节点**。「节点内展开」否决。

## 1. 需要做这个决定的原因

白板今天只呈现文档级的节点与边。文档内部的可验收结构全部不可见，其规模实测自
**提出本决定时（FR-31…36 增补前）的工作树：22 份文档（含本决定自身）、51 条
关系声明（含本决定的 5 条）**：

| 事实 | 实测 | 度量方式 |
| --- | --- | --- |
| 正式编号条目 | **186 条**（spec-00001：30 FR + 110 AC；rule-00001：19 BR + 27 AC） | 按各 README 的 id 语法 grep |
| record 验收行 | 136 行，引用 129 个不同的 AC | `(spec\|rule)-00001-AC-\d+\.\d+`，只数 `record/record-*.md` |
| 无任何验收行引用的条目 | **BR-3 … BR-9 共 7 条**（FR 为 0 条） | 见下方口径 |

**口径要写明，因为初稿又错了一次**：初稿把 `record/README.md` 示例表里的 id
也数成了真实引用（报 140 行 / 130 个 AC / 缺口 6 条）——而按 spec-00001 §1 与
rule-00001 §1 自己的定义，README/TEMPLATE 根本不是文档。纠正后缺口多出的正是
**BR-3**：它的 AC 只在 README 的示例行里出现过。错法与 decision-00003 §1 的教训
同型：代理口径当真实口径报。上表第三行以「任一真实 record 中出现过该条目的任一
AC id」算作引用，含散文引用，仍**偏宽**——真按验收门禁的口径（每条 AC 都要有
结果为 `pass` 的清单行）缺口只会更多。要害在于：这个缺口今天**只能靠写脚本
发现**——本表的数字就是临时脚本跑出来的，而 `CLAUDE.md` §6 的 resolve 门禁每轮
都需要这个答案。

另一个已经发生的事实：`record-00003` 的 front matter 写的是
`verifies: [spec-00001-FR-28, spec-00001-FR-29, spec-00001-FR-30]`——细粒度
条目 id 已经进了关系声明（`docs/record/README.md` 明文允许），而 `spec-00001-FR-2`
会把指向非文档 id 的边标为异常。**细粒度信息已经存在，白板不但读不了，还会把它
当错误**（issue-00005 §8 已把这三条断链记为残留状态）。这个冲突的裁定见 §5。

## 2. 决定

五条，按解决的问题分开：

| # | 做法 | 解决 |
| --- | --- | --- |
| 1 | **检视面板（主）**：选中 spec/rule 节点时，右侧面板列出其全部需求条目（FR/BR），含 id、正文与 AC 计数 | 「这份 spec 里有什么」不用打开编辑器逐屏滚 |
| 2 | **覆盖三态**：每条条目携带由验收行推导的覆盖状态——已验证 / 未通过 / 未覆盖 | resolve 门禁的缺口从脚本产物变成一眼可见 |
| 3 | **悬停联动**：悬停面板条目时，选中文档与相关 record 之间的边转强调态、标签换成被引用的 AC id | 「这条 FR 的证据在哪份 record」 |
| 4 | **子画布（辅）**：面板顶部「展开为子画布」下钻——条目、AC、验收行成为一等节点，面包屑返回 | 验收链路（FR→AC→验收行）与断口的整体审查 |
| 5 | **不变量：条目不上顶层图** | 顶层图的节点数与边数不因条目而变 |

覆盖三态的定义与判定次序（先命中先出）：**未通过**——存在结果非 `pass` 的引用行
（`fail`、`n/a` 一律入此态，白板不区分未过的原因，原因去 record 里读）；
**未覆盖**——该条目没有任何 AC，或存在没有任何引用行的 AC（零 AC 是最该暴露的
缺口，不得落进已验证；覆盖按 AC 逐条要求，与 `CLAUDE.md` §6「every GWT has a
passing test」同口径）；**已验证**——其余。

分工与同类产品一致（Figma / Linear 的「画布紧凑、细节进面板」，Miro Frame 的
下钻）：**单击看面板，下钻才进子画布**。面板与编辑器互斥占用右侧槽位，代价
明写在 §4。

## 3. 考虑过的其他选项

| 选项 | 为什么不选 |
| --- | --- |
| **节点内展开**（选中/展开时把条目列在节点卡片里） | spec-00001 一个节点要列 30 行、每行还挂 AC——按现行节点高度估算展开后独占半屏，邻居与边（白板的本体价值）被挤出视野。只在条目 ≤5 条时可用，而本仓两份文档分别是 30 与 19 条 |
| **条目做顶层图的一等节点** | 节点数从 22 涨到 208（22 + 186 条目），近 10 倍；decision-00003 刚为 39 条边的可读性立过规，条目上图直接推翻它的全部实测基础 |
| **悬停即览卡**（hover 节点浮出条目摘要） | 不否决——它是面板的轻量入口，但承载不了 30 行列表、覆盖状态与联动。若后续要做，是面板的补充而不是替代，不在本轮 |
| **画布→面板的反向联动**（点边或 record 节点定位到条目行） | 有效但正交，且依赖面板先存在。留作后续杠杆，不在本决定内 |
| **覆盖执法**（未验证则阻止状态流转/推进） | 白板呈现缺口、不执行门禁——门禁属 `rule-00001` / 流程文档的职权；执法需要先裁定「谁有权代表门禁」，超出本轮 |

## 4. 后果

**接受的代价**

- **白板第一次解析 front matter 之外的正文**。条目有两种声明形态都要认：列表项
  （`- **spec-00001-FR-1** …`）与决策表行（`| **rule-00001-BR-2** | …`，
  rule-00001 的 BR-2…BR-9 就是这么写的）。写法即契约：正文写法漂移，解析就失灵
  ——`spec-00001-FR-33` 只能把不合式的行兜底为「无法归属」，不能阻止漂移本身。
- **面板与编辑器互斥占用右侧槽位**，无法边看条目边改正文。要那个场景的是子画布
  （只读）或后续拆双槽——先付互斥的代价，等真实使用证明需要再拆。
- 两条**未经验证**的前提，明写在此以免被当成已证事实：一是 30 行的面板列表读得动
  （decision-00003 对 17 行关系列表留过同样的存疑，同样未验）；二是悬停联动把边
  标签在关系字段名与 AC id 列表之间来回切换时不产生可感的抖动。（初稿此处担心的
  第三条——「record 侧的边是异常边时联动劣化」——随 §5 裁定一消解：可解析的
  细粒度引用就是正常边。）二者都在落地后按真实数据看一眼再定。

**得到的**

- 「哪条 FR/BR 还没有验收证据」从脚本产物变成选中节点即见；resolve 门禁的核验
  第一次有了非脚本的读法。
- 细粒度验收链路（条目→AC→验收行）有了可视形态（子画布），审查一份 spec 的
  验收完整性不再需要在三个文件夹之间人肉对照。
- 顶层图零改动：节点数、边数、布局、边三态（decision-00003）全部原样。

**不变的**

- 顶层图的节点与边只来自文档与 front matter 声明（决定第 5 条不变量）。
- `docs/` 数据模型与各 README 的 id 语法——白板读既有约定，不新增任何标注负担。

## 5. 裁定

本节曾是 Open Questions；前两问由域主裁定，第三问是审计发现后按既有口径的
派生裁定，已随本决定的接收一并确认。

- **裁定一（原 OQ-1，取 (a)，域主已裁）**：关系字段指向**存在的**需求条目或
  AC id **不是异常**——边落到条目所在的文档，关系列表照常列出所声明的细粒度 id；
  仅无法解析的 id（既非存在的文档，也非存在的条目/AC）才标异常。这构成对
  `spec-00001-FR-2` 的修订（新增 `AC-2.5`/`AC-2.6`）。现行实现把 `record-00003`
  的三条 verifies 边标异常，该缺口 issue-00005 §8 已记为残留状态，由落地本决定
  的 plan 消除，不另立 issue。
- **裁定二（原 OQ-2，域主已裁：不区分）**：覆盖推导不区分 record 的 status——
  record 状态管文档生命周期，不管证据效力。`spec-00001-AC-32.5` 即此口径。
- **裁定三（审计产物，派生）**：`docs/record/README.md` 允许验收行
  直接引用条目 id（`| spec-00001-FR-14 | … |`），本决定的推导对这种行取：其
  **非 `pass`** 结果使条目「未通过」（报警同权）；其 **`pass` 不能替代逐 AC
  引用**（per-AC 覆盖是 §2 的既定口径）；它是合法行，不入「无法归属」。
  `spec-00001-AC-32.9`/`AC-32.10`。此条是 per-AC 口径的推论，随本决定的接收由
  域主确认。

  写作时尚未动它）。
- 后续任何「把更多文档内部结构画上白板」的提案：先回答「它为什么不是面板/子画布
  的一行」，再谈上图。
