# Decision: 桌面通知取页面级 Notification API，只在离场时弹

> 推翻 `decision-00009` §2 第 8 条对「板外通知」的范围外维持：等待输入与
> 会话结束在用户**离场**（页面隐藏，或窗口失焦）时送达桌面。路线取页面级
> Notification API（无 Service Worker），页面可见且聚焦时仍由提示条与
> 徽标承载；标签页关闭、浏览器退出后**有意不送达**——离场即退订。

## 1. 需要做这个决定的原因

- `spec-00003` 的等待徽标与结束提示条只活在页面里。域主对并行会话的人工
  测试（2026-08-23，实录）证实：不开着页面就会漏掉「会话在等我」，只能
  来回切窗口盯——这正是 `decision-00009` §2 第 8 条搁置板外通知时缺少的
  瓶颈实录。
- 技术路线已由 [analysis-00001-out-of-board-notifications](../analysis/analysis-00001-out-of-board-notifications.md)
  盘过：页面级 Notification API（A）、SW + Web Push（B）、Declarative
  Web Push（C）、服务端直发系统通知（D）四条的覆盖面与代价见其 §3。

## 2. 决定

| # | 做法 | 理由 |
| --- | --- | --- |
| 1 | **路线取 A**：页面级 Notification API，无 Service Worker、无推送服务、无服务端通知代码 | 覆盖真实痛点（页面开着但在后台/浏览器失焦）；权限模型与通知渲染是将来多人形态升级 Web Push（B/C）的台阶，不留迁移债；D 与多人/远程形态不兼容（服务端不在用户本机时够不着桌面），且「关了浏览器还收到通知」不符合离场预期——两点均为域主裁定 |
| 2 | **只在离场时弹**：离场 = 页面隐藏**或**其窗口失焦（两个信号的判定口径属 design——仅按页面隐藏判定盖不住「窗口可见但在别的窗口干活」这一主场景，审计发现）；页面转入离场时为**已在等待输入的会话补发**（每会话每次等待至多一条）；页面可见且聚焦时由既有提示条与徽标承载，不重复弹 | 「不在页面」的精确语义就是隐藏 + 失焦两个半边；不补发则「离开时它已经在等」的用户永远收不到——正是要解决的漏看 |
| 3 | **事件集**：等待输入置位时；会话结束时（正常退出/失败/终止，含启动失败）。等待解除不通知 | 「谁在等我」与「谁完成了」正是离场时会漏的两类；解除是用户自己操作的结果，无需提醒 |
| 4 | **启用是显式动作**：顶栏「桌面通知」开关，开启时才请求浏览器权限（权限已授予则静默生效、不再请求）；**关闭立即安静**、开关两态均持久于浏览器本地（不入 `docs/`）；缺省关闭，绝不开页即弹权限框 | 未经请求的权限弹窗是浏览器已在惩罚的反模式（Chrome quieter UI）；关闭必须即刻可信，否则开关是假的 |
| 5 | **点击通知**：**请求**聚焦白板页面（能否前置属浏览器/系统策略，尽力而为）并在页面呈现时于终端呈现对应会话（与会话面板点击同构，含目标不在图上的就近处置） | 通知的下一步动作就是去应答；聚焦不是页面能单方保证的，承诺按事实收窄 |
| 6 | **通知内容只含会话种类、文档 id 与状态**，不含正文片段；**同一会话后到替换先到**（复用同一标识），同刻至多一条 | 系统通知会落通知中心，最小化外泄面；等待→结束叠两条是噪音，替换是通知标识的既有能力 |
| 7 | **多窗口同开时可能重复弹，作为已知边界接受**；被浏览器冻结/丢弃的后台标签，通知**可能不送达且恢复时不补发**——弱语义同 `spec-00003-FR-6`，回到页面时徽标与面板仍如实 | 本地单人工具多窗口罕见，跨窗口去重（BroadcastChannel）为罕见情形加机制不值；丢弃的标签脚本已终止，「迟到」是粉饰、「可能不送达」才是真话 |

## 3. 考虑过的其他选项

| 选项 | 结论与理由 |
| --- | --- |
| D 服务端直发系统通知 | **否决**（域主裁定）。多人/远程形态下是死路（迁移即推倒重来）；标签页关闭、浏览器退出后仍送达不符合「离场即退订」的预期 |
| B SW + Web Push（自签 VAPID） | **否决**。为「标签页关闭可达」引入公网绕行（FCM/Mozilla）、SW 与订阅设施——而该情形本决定裁为有意不送达；将来多人形态需要时再升级，A 是其台阶 |
| C Declarative Web Push | **否决**。2026 年仅 Safari 系可用，Chromium/Firefox 未落地；同样绕推送服务 |
| A+D 组合（页面开着走 A、没开走 D） | **否决**。D 的两条否决理由不因组合消失 |
| 页面可见时也弹系统通知 | **否决**。与提示条双重打扰；可见时的承载已由 `spec-00003` 定 |
| 缺省开启、首次事件时请求权限 | **否决**。未经请求的权限框；显式开关一次即永久 |

## 4. 后果

**接受的代价**

- 标签页关闭、浏览器退出后收不到任何通知——**有意的**：离场即退订；回到
  页面时徽标与面板仍然如实（`spec-00003` 既有语义）。
- 需要一次浏览器权限授权；被拒后该浏览器内无法再程序化请求，只能提示用户
  去浏览器设置手开。
- 后台标签页被浏览器冻结/丢弃时，通知可能**不送达**且恢复时不补发（弱
  语义，允许；徽标与面板兜底）。
- 多窗口同开可能重复弹（已知边界）。
- 「终止」的通知在实践中不可达（终止总在页面可见时发起、被可见抑制；
  服务端关停的结束随通道关闭不送达）——不为其造第二条通路。

**得到的**

- 页面在后台、窗口失焦时，等待输入与会话结束直达桌面——不必来回切窗口。
- 零基础设施、零服务端改动、离线可用；多人形态的升级路径（Web Push）保持
  畅通。

**不变的**

- 页面可见时的承载不变：提示条（FR-7）与徽标（FR-6）照旧。
- 服务端不新增任何通知职责；`spec-00003` 全部语义不动。

## 5. 这个决定约束什么

- `spec-00004-whiteboard-desktop-notifications`：全部 FR 按本决定落地。
- `design-00002-whiteboard-ui`：顶栏开关控件、通知触发与点击回跳的界面侧
  （修订轮，由 plan 轮列任务）。
- `decision-00009` §2 第 8 条：其「板外通知维持范围外」被本决定推翻——
  已在该行原地追注。
- `spec-00003` §6「板外通知」范围外条目：由 `spec-00004` 接管，不就地
  删除（移除属 `spec-00003` 自己的修订轮，plan 轮列任务——沿
  `spec-00002` 先例）。
- `CONTEXT.md`（随 spec-00004 接收）：新增「桌面通知」「离场」两条术语
  （前者 _Avoid_ 系统通知/浏览器通知/推送通知，与「变更推送」词条排除的
  「推送通知」显式区分）；修订「等待输入」——「只驱动徽标与通知」明确为
  「徽标、提示条与桌面通知」。
- 站立约束：不得为本地单人形态引入推送服务或服务端桌面通知；升级 Web
  Push 属将来多人形态的新一轮。
