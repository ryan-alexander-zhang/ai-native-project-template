# Decision: 共写会话——第五种会话种类，推翻 decision-00008 §3 对「新建走 agent 会话」的否决

> 裁定新增会话种类**共写**：对任意类型的一份 `draft` 文档发起多轮 agent
> 对话，起草或改写其正文；顶栏新建增加「共写」模式（建档后自动接续会话），
> 推翻 `decision-00008` §3 的否决行；外部材料（仓库外文件、URL）经用户在
> 终端逐动作授权读取。评审门全部不动。

## 1. 需要做这个决定的原因

域主的目标：所有文档都可以通过与 agent 的对话编写、新建、修改。对现状的
全量核对（本决定由该评审对话促成，无来源文档可指）发现覆盖是系统性断链：

- 16 种类型中仅 5 种（idea/prd/spec/rule/design）存在任何 agent 写作或
  修订通路；`analysis`、`decision`、`integration`、`reference`、
  `operation`、`prompt`、`report` 七种的全部内容生命周期只能手工编辑。
- 新建对全部 10 种入口类型是手工模板填写（`spec-00001-FR-53`）——
  `decision-00008` §3 曾明文否决「新建走 agent 会话」，理由是「空手起草
  比有源推进难，首版质量不稳」。
- 没有修订会话：修订轮（`rule-00001-BR-3`）只重开既有评审动作，对不可
  澄清、不可审计的类型不提供任何 agent 动作；`active` 文档的内容 agent
  完全触不到。
- 澄清与审计的写授权是窄授权（未决点入 Open Questions、有定论修入正文），
  覆盖不了「按对话结论改写正文」。

域主裁定推翻 `decision-00008` §3：共写不是当年否决的「空手起草」——人每
轮在环给意图、给材料、当场 review，评审门原封不动，首版质量的担忧由此
消解。

## 2. 决定

| # | 做法 | 理由 |
| --- | --- | --- |
| 1 | 新会话种类**共写**（SessionKind 第五种）：对任意类型的一份 `draft` 文档——work item 亦可在 `open` 状态——发起交互式终端会话，agent 按用户的意图与材料起草或改写该文档正文，多轮往复；不是评审动作，不改变状态（`rule-00001-BR-28`、`rule-00001-BR-29`） | 「任意类型的 `draft` 或 `open` work item」是一条可判定规则，免维护类型清单，且与手工编辑现状对齐（`open` 的 plan 实践中本就在被修——域主裁定）；spec/rule/design 上它与澄清、审计互补而非替代 |
| 2 | 顶栏新建增加**共写模式**：按 `spec-00001-FR-53` 原样建档 commit 后，自动对新档发起共写会话；「空白模板」模式原样保留 | 推翻 `decision-00008` §3 的否决行；建档与共写解耦复用，FR-53 的 id 分配、模板预填、拒绝分支全部不必重做 |
| 3 | **读宽写窄**：agent 读仓库外本地文件与 URL，经用户在会话终端逐动作授权（用所选 CLI 自身的权限机制，白板不代答、不预授权、不压掉询问）；落地写域仅限目标文档与合式新建的 `reference` 文档（`rule-00001-BR-30`），执行层为**白板收束过滤**（`spec-00006-FR-6`，域主裁定）——`spec-00001-FR-13` 的「不做 git 回滚兜底」半句与 `spec-00001` §6 的写域排除在其修订轮对共写改写 | 域主明确要求支持仓外材料，「哪怕需要在终端授权」；写域不随读域放宽，且收束过滤确定性强、不依赖各 CLI 权限能力的差异 |
| 4 | **文档即记忆**：会话之间不留隐藏状态，新会话从文档现状读起；任务指令要求外部材料中支撑结论的内容写进正文、或落成 `reference` 文档（其 `informs` 仅在指向 spec/design/plan 时可挂，`reference` 文件夹 README 的既有约定） | 外部材料是会话级的，下一轮读不到这一轮授权过的东西；价值必须留在知识库，不能留在一次性会话的记忆里 |
| 5 | **轮流持笔**：agent 等待输入时用户可直接在编辑器改目标文档（缓冲随 agent 写入重载，故保存无冲突），手改在下一轮告知 agent；agent 正在写时编辑器只读；差异标示留作后续增强 | 「工作区」的核心体验——review 不是只读旁观；只读/可编辑随回合切换避免双写冲突 |
| 6 | 评审门全部不动：接收仍是人点、OQ 门（BR-12）仍拦、spec/rule/design 接收前仍须审计、`active` 须先经修订轮降 `draft` 才可共写 | 共写扩的是写作通路，不是质量豁免 |

## 3. 考虑过的其他选项

| 选项 | 结论与理由 |
| --- | --- |
| **扩澄清/审计的写权限为通用改写** | **否决**。窄授权（BR-11、BR-22）正是这两个评审动作可审计性的来源——评审者同时是改写者，评审就失效了 |
| **只对域主点名的七类开放** | **否决**。类型清单要维护、要修 BR 才能扩；「任意类型的 `draft` 或 `open` work item」一条谓词覆盖点名七类，且到达 plan/task/issue/record 的修订缺口——record 在 `draft` 期、work item 在 `draft` 与 `open` 期（它们由推进出生、此前从无 agent 修订通路） |
| **编辑器内嵌 AI 补全（无会话形态）** | **否决**。绕开会话注册表、并发正则、会话历史、agent 选择与终端授权的全部既有机制，另起一套通道 |
| **白板自建抓取/代理承载 URL 材料** | **否决**。抓取与授权能力属所选 CLI，白板只负责把材料递进任务指令；自建代理即自建一套权限模型 |
| **维持现状** | **否决**。断链是系统性的（§1），与域主目标直接冲突 |

## 4. 后果

**接受的代价**

- `decision-00008` §3 的顾虑部分仍真：首版质量依赖对话质量。缓解：人每
  轮在环，评审门不动，写坏的 draft 不会未经接收流入 `active`。
- 共写会话持有真实写权限，误写风险存在。缓解：写域仅目标文档与新建
  reference（BR-30 落地校验）、一会话一 commit、git 可回退。
- 终端授权交互的形态因 CLI 而异，白板不统一它——体验一致性让位于不自建
  权限模型。
- 「任意类型」意味着 record 也可共写——record 是证据文档。审计查实
  「record 不改写」此前并无成文约定，随本决定补立：「已接收的 record 是
  证据、不改写，勘误走新 record」写入 `docs/record/README.md`，任何写作
  通路（手改、修订轮、共写）不为其开豁免（域主裁定：约定把关，不在规则
  层排除 record——`draft` 期的 record 本就该能被共写撰写）。
- 共写对正文的全量写权可及 Open Questions 小节（BR-12 的促进门读的正是
  它）。域主裁定不加机器限制：共写每轮人在环、促进仍需人接收，对话中
  答定的问题当场关闭是共写的正当用法。

**得到的**

- 全部 16 种类型获得 agent 写作/修订通路，覆盖断链清单的全部内容项。
- 「一句想法 → agent 共写成 idea」「给材料 → agent 写 design → review
  → 再改」两条域主场景成立。
- 外部材料的知识沉淀有了成文机制（蒸馏进正文或落 reference）。

**不变的**

- 答疑只读（`decision-00012` §5 站立约束）；澄清、审计的窄授权与适用
  类型；FR-53 手工新建模式；推进会话的既有形态。
- `decision-00008` 除 §3 被推翻的一行外全部继续有效（修订轮、新建入口、
  会话可达性）。

## 5. 这个决定约束什么

- [rule-00001-docs-workflow](../rule/rule-00001-docs-workflow.md) ——
  `BR-28`（共写定义）、`BR-29`（仅 `draft`）、`BR-30`（写域）由本决定
  产生；`BR-21` 的「修订走编辑、推进或澄清」补入共写。
- [spec-00006-whiteboard-co-write](../spec/spec-00006-whiteboard-co-write.md)
  —— 共写的系统行为规格由本决定给出路线。
- 白板代码的 `SessionKind` 枚举：第五种为共写；实现须落在本决定与
  spec-00006 均 `active` 之后的 plan。
- 后续任何「让评审动作承担通用改写」或「绕开会话机制的 AI 写作形态」的
  提案：先出示本决定 §3 的对应否决理由已失效的证据。
