# Decision: 白板增设左侧导航栏与缩略图，作为「浏览」的出路

> 在工作区左侧加一条可收起的导航栏：按类型列归为类型组、组内按行序列出全部
> 文档，点一行即定位并选中；画布右下角加缩略图。命令面板仍是唯一的检索入口——
> 导航栏解决的是「不知道名字、想翻」，不重开常驻搜索框。

## 1. 需要做这个决定的原因

- `decision-00002` §4 明写接受了「纵向无界」的代价：列高等于该类型的文档数，
  只能靠平移与缩放看完，命令面板是「找到某一份」的既有出路——也是至今唯一
  的出路。design-00002 §2 落地时的快照是 17 份文档；今天 105 份（含本轮三
  稿），`plan` 列 24 行、`record` 与 `issue` 各 23 行，按 `layout.ts` 的行距
  140px 计一列约 3170 … 3310px，超出任何视窗两倍以上。
- 命令面板（`spec-00001-FR-26`/`FR-27`）要求用户先知道 id 或标题的片段。
  「看看 plan 里都有什么」「找那份关于通知的 spec 但记不清名字」这类**浏览**
  动作，今天只能在画布上拖着找。
- 域主于 2026-09-02 的评审对话中提出该需求并逐项裁定（归组依据、过滤框、
  行内容、子画布行为、缺省态），并要求一并加缩略图。

## 2. 决定

| # | 做法 | 理由 |
| --- | --- | --- |
| 1 | **工作区左侧增设导航栏**：可收起、宽度可调，列出图上全部文档 | 同类工具（Figma 图层面板、Miro Frames 面板、Obsidian 文件树）解决同一问题的共同形态：树/列表 + 点击定位 + 选中同步。它是浏览的出路，与命令面板（检索）互补而非替代 |
| 2 | **按类型列归为类型组，不按物理目录**：组序即 `decision-00002` §2 的列序，组内即行序 | 导航栏是画布的镜像：组对应列、行对应行，读者在两处看到同一个顺序。目录与类型今天恰好同名，但布局规则取 front matter `type`——按目录归组会在 `type` 缺失或与目录不符时与画布分歧 |
| 3 | **导航栏不带过滤框**，检索仍走命令面板 | design-00002 §2 已裁定把常驻搜索框换成命令面板并接受可发现性代价；导航栏加过滤框等于把那个决定翻回一半、并出现两个检索入口。域主裁定 |
| 4 | **每行呈现状态、id 与标题**；组头呈现类型名与计数 | 与节点的信息层级一致（§4：状态、标题、id），足以辨认；不呈现关系、覆盖等重内容——那是检视面板的事 |
| 5 | **点击一行 = 定位并选中**，走命令面板同一通路；处于子画布时**退出子画布**再定位 | 去某份文档是顶层动作（`spec-00001-FR-36` 与面包屑 Board 已如此）；一条通路两个入口，不另造行为 |
| 6 | **选中变化同步到导航栏**：高亮该行并滚入视野，所在组折叠则展开 | 反向同步（VS Code 的 auto reveal）让画布点选后能在列表里看到「它在哪、旁边是谁」 |
| 7 | **导航栏缺省展开、各类型组缺省折叠；开合、宽度、各组展开态持久于浏览器本地**；缺省宽度与最小宽度由 design 自决 | 域主裁定导航栏缺省展开；类型组缺省折叠系域主第二次裁定（初版全展开，百余份文档首屏杂乱）——首屏是一份目录，点开才见行。开合与展开态进「呈现状态」枚举，宽度走既有面板尺寸记忆的口径；三项都不进 `docs/`，与主题、通知开关同一本地层 |
| 8 | **画布加缩略图**（React Flow 内建 `MiniMap`），节点按状态着色，顶层与子画布皆有 | 缩略图回答「我在整图的哪」，导航栏回答「那份文档在哪」——两问不同，一个替代不了另一个；内建组件成本几行 |
| 9 | **不做虚拟化** | 102 行的列表离需要虚拟化差一个量级；先按实际规模落地 |

## 3. 考虑过的其他选项

| 选项 | 结论与理由 |
| --- | --- |
| 只加缩略图 | **否决**。缩略图里的节点没有名字，解决不了「按名字翻」；它是补充，不是方案 |
| 导航栏带过滤框 / 恢复常驻搜索框 | **否决**（域主裁定）。与 design-00002 §2 的命令面板裁定相悖，且产生第二个检索入口；⌘K 继续承担检索 |
| 按物理目录归组 | **否决**。与画布的列序规则（front matter `type`）在 `type` 缺失或不符时分歧；导航栏应镜像画布（decision-00018 部分推翻：分列仍按 `type`，目录得作类型列内的第二级归组） |
| 画布内折叠或分页长列 | **否决**。改变布局规则本身，`decision-00002` 已明确不做纵向分页或折叠；且折叠后节点位置不再可预期（decision-00018 推翻：按目录折叠，位置在给定展开态下仍可预期） |
| 导航栏放右槽、与编辑器/检视面板共用槽位 | **否决**。右槽的编辑器优先规则（§9）会让导航在编辑期间消失；导航须常在 |
| 手动排序或收藏 | **否决**。引入 `docs/` 之外的用户状态与工具的无状态前提相悖（`decision-00002` §3 同一理由） |
| 切换导航栏的快捷键 | **搁置**。未提出需求；顶栏按钮足够，有实际需要再加 |

## 4. 后果

**接受的代价**

- 缺省展开的导航栏占去工作区约五分之一宽度，画布默认变窄；缓解是可收起、
  可拖窄，且开合态被记住。
- 收起或展开导航栏改变画布宽度时**视口不重居中**——与打开终端面板同一
  口径（issue-00006 的重居中只在选中动作后）。用户可再点一次行或节点。
- 浏览器本地新增三处持久状态（开合、宽度、展开组）；清除站点数据即回缺省，
  不影响 `docs/`。
- 缩略图与 `Controls` 各占画布一角（右下 / 左下），窄画布时压缩可视区域；
  接受。

**得到的**

- 「纵向无界」的实际代价被抵消：任何一份文档两次点击可达，不再依赖记得名字。
- 画布点选后能在列表里看到上下文（同类型的邻居与总数）。
- 缩略图给出整图位置感，长列平移不再迷路。

**不变的**

- 画布布局规则（`decision-00002`）、节点呈现（design-00002 §4）、命令面板
  的检索与跳转语义（`spec-00001-FR-26`/`FR-27`）全部不变。
- 右槽三态与终端面板的占位规则不变；导航栏是工作区行内新增的第三个区域，
  不参与右槽互斥。
- 零服务端改动：`GET /api/graph` 与 `GET /api/config` 的契约不变，归组由
  页面从既有载荷推导。

## 5. 这个决定约束什么

- `spec-00008-whiteboard-navigation-sidebar`：全部 FR 以本决定为前提。
- `design-00002-whiteboard-ui`：§2 布局增左侧区域；新增一节承载导航栏与
  缩略图的界面设计（第二十四轮修订轮）。
- `plan-00024-whiteboard-navigation-sidebar`：落地本决定与 spec-00008。
- 站立约束：导航栏不得引入检索输入框（检索归命令面板）；归组依据不得改为
  物理目录（decision-00018 部分推翻：分列依据不得改为目录，目录得作类型列内的
  第二级归组）；不得为导航栏引入 `docs/` 之外的排序或收藏状态。后续落到本决定
  之下的 `plan` 回填进本文件的 `constrains`。
