# Decision: 边的可读性靠焦点与列表，不靠走线

> 39 条边同时全强度呈现，图变成一团乱麻。处置是**焦点 + 上下文**：默认全部弱化、
> 选中时强调；中枢节点另给一份关系列表。正交走线经实测**否决**。

## 1. 需要做这个决定的原因

白板画出全部关系边之后（`issue-00002` 的修复），真实仓库的图不可读了。以下全部
实测自**本决定写作时的工作树：19 份文档、39 条边**（含本文与 plan-00004 自身）：

| 现象 | 实测 | 度量方式 |
| --- | --- | --- |
| 边从节点卡片上穿过 | **53 处** | 端点到端点的直线段与节点矩形求交，排除两端自身 |
| 跨一列以上的边 | 24/39 | `verifies` 平均跨 5.7 列（n=3），`blocks` 2.8（n=8） |
| 常驻标签 | 39 个，密处直接叠字 | 每条边无条件带 `label` |
| 中枢 | `spec-00001` 牵连 **17/39 条边（44%）** | — |

**度量口径要写明，因为我第一次写错了**：初稿的「106 处」用的是「两端之间的列里
有多少个节点」这个代理指标，并把它当成了真实穿透数报出来。真实穿透是 53——问题
仍然真实，但被我夸大了一倍。凡后续再引用这些数字的，以本表的口径为准。

要害仍然成立：**噪声量（53 处穿透 + 39 个标签）大于边的数量（39）**，所以「少画
一些边」不是最直接的杠杆。

## 2. 决定

三条，按解决的问题分开：

| # | 做法 | 解决 |
| --- | --- | --- |
| 1 | **默认弱化**：全部边照画，但低对比、细线、**不显示标签** | 39 个标签的叠字，以及边与节点抢注意力 |
| 2 | **选中即聚焦**：选中节点后，它的边转强调态（高对比、显示关系名、绘于节点之上），其余边与无关节点一并压弱 | 「这份文档跟谁有关」这个具体问题 |
| 3 | **关系列表**：选中节点的工具栏按关系字段分组列出全部关系与方向，点击即跳转 | 中枢节点——它的边多到任何几何手段都分辨不了 |

第 3 条不是锦上添花，是第 2 条的兜底：`spec-00001` 有 17 条边、连着 **16 个不同
的邻居**，全图除它自己外只有 2 个节点会被压弱。**对中枢节点，聚焦几乎不起作用**，
只有把关系读成一份列表才是可读的。次高的 `design-00002` 只有 6 条边、10 个节点
会被压弱——聚焦对它完全够用。也就是说列表是为**少数中枢**存在的，不是为每个节点。

边**始终全部画出**（`spec-00001-AC-1.1` 不变），弱化态仍能一眼看出图的疏密与
孤立节点——那正是 `spec-00001` §2 的 S1「一打开就看清依赖链与卡点」的依据。

## 3. 考虑过的其他选项

| 选项 | 为什么不选 |
| --- | --- |
| **默认不画边，点击才显示** | 直接推翻 S1：点击之前白板退化成一堆卡片，「一眼看清依赖链」这条立论没有了。且对中枢无效——点 `spec` 仍是 17 条边、**38 处穿透**，是全图 53 处的 72% |
| **「完整 path」＝显示整条血脉（传递闭包）** | 两种读法都不成立。**无向**可达：全图是一个连通分量，**任何**节点的可达集都是全部 19 个——点谁都点亮整张图。**有向**（顺着声明箭头）可达：`idea` 是 0、`prd` 是 1、`spec` 是 2——几乎什么都点不亮。一个太多、一个太少，中间没有可用的读法 |
| **正交走线：让边只走列间沟槽与行间空隙** | 见 §4「被实测否决的方案」 |
| 第三方绕障边（A* 一类） | 引入一个维护状况不明的依赖，去解一个我们已经证明不该解的问题（同上） |
| 层次化边捆绑（hierarchical edge bundling） | 为 39 条边引入一整套曲线捆绑算法；且捆绑之后单条边更难追踪，与「看清这一份依赖谁」相反 |
| 按关系字段过滤（勾选显示哪些字段） | 有效但正交，且需要用户先知道该关哪个。留作后续杠杆，不在本决定内 |

## 4. 被否决的方案：正交走线

这是本决定最初的首选，也是我先提给产品负责人的方案，理由看着很顺：布局是严格
网格，列间 96px、行间 48px 都是**由构造保证空着**的走廊，长边完全可以「横向出
节点 → 在沟槽里纵向走 → 在某条空带上横向跨越 → 纵向入目标」，结构上不可能压到
任何卡片。

**第一次模拟的结论是错的，必须先纠正。** 初稿写的是「20 条长边挤在同一条带，
48px 的行间空隙放不下 20 条泳道」。那段有两个错误：候选空带只取了「栅格上方」与
「栅格下方」，而没有按自己声明的「取最近的空带」把**行间沟槽**也算进去；而被选中
的「栅格上方」是无界画布，却拿 48px 的行间空隙去衡量它的容量。把候选集补全后重跑：

```
候选空带 = 栅格上方 · 各行间沟槽 · 栅格下方
最近空带（并列时取先者）→ 上方 6 条 / 沟槽0-1 13 条 / 沟槽1-2 4 条 / 沟槽2-3 1 条
最挤的一条带同时重叠的边数（按 x 区间着色，不是每边一条泳道）= 11
```

也就是说：**最坏 11 条泳道**，48px 的沟槽按 4px 间距刚好放得下。正交走线在本仓的
规模上**是可行的**——这一点初稿说反了。

否决它的理由因此换成两条，都与容量无关：

1. **它解决不了真正的问题。** 17 条边指向 `spec`，无论怎么走线都要收束到同一个
   节点上。「有 17 样东西指着这里」是数据的真实属性，不是画法问题。走线能把 53 处
   穿透清零，却让中枢一点也不更可读——而中枢正是最难读的那个。
2. **它的代价与收益不对称。** 换来的是一个与布局强耦合的走线层（泳道分配、空带
   选择、并列时的取舍规则都要自己维护、自己测），而它要修的 53 处穿透，在「默认
   弱化 + 强调态抬到节点之上 + 无关节点压弱」之下已经不再妨碍阅读。

保留的可能：若将来图变得又窄又深、或穿透在弱化态下仍然碍眼，走线是**可行且已经
量过**的下一步。重新评估时请连同上面这段一起读——尤其是「按 x 区间着色算泳道」
而不是「每条边一条泳道」这个口径。

## 5. 后果

**接受的代价**

- **53 处穿透原样保留**。弱化态下它们是浅色细线从卡片下经过，可以接受；强调态
  下靠「绘于节点之上 + 无关节点压弱」求可读，而不是靠不相交。这是明知的取舍。
  「边可以抬到节点之上」已实测确认：`.react-flow__edges svg` 是 `position:
  absolute`（`@xyflow/react/dist/style.css`），故其 `z-index` 对节点层有效。
- **弱化态没有标签**，想知道某条边是什么关系必须先选中一端。代价换来的是默认视图
  可读。
- **中枢节点的图仍然密**。列表是出路，但图本身不会变清爽——这是数据决定的。
  两条**未经验证**的前提，明写在此以免日后被当成已证事实：一是「17 行的关系列表
  读得动」，二是选中中枢时同时出现的十余个边标签不会重新构成叠字。二者都要在
  落地后按真实数据看一眼再定，必要时给标签加密度阈值。（第五轮落定：悬停态的
  AC 标签按边计、阈值 3、超出折叠为「首个 id +N」——`spec-00001-FR-34` 修订，
  域主裁定。选中态关系名标签的叠字问题不在该次范围，此预留对它仍然有效。）
- **多一处 UI 状态**：边的呈现依赖当前选中项，节点与边的样式都要随选中变化。

**得到的**

- 默认视图从「39 条线 + 39 个标签」变为一层淡背景，图的形状（哪里稠密、谁是孤岛）
  第一次真正可读。
- 「这份文档依赖谁」有两条互补的答案：图上高亮，和列表逐条读。
- 不引入任何依赖，不引入走线几何，`layout.ts` 保持纯函数不变。

**不变的**

- 全部边照画（`AC-1.1`）；布局规则（`decision-00002`）一个字不改；后端与
  `docs/` 数据模型不受影响。
