# Decision: 澄清改为 agent 逐题拷问，新增答疑——两个方向、一套会话通道

> 节点上的两类提问按方向切分：**澄清**是 agent→负责人（拷问业务问题，产出
> Open Questions 或文档修订，仅 `draft` 的五种可澄清类型），**答疑**是负责人
> →agent（看不懂就问，多轮讨论，按结论修订文档，任意类型任意状态）。旧的
> 手动填写待澄清点入口**废弃，不留兼容**。提示词取「代码持有共享骨架 + 流程
> 配置持有每类型一行焦点行」的最小可配形态；澄清进度以 JSON 状态文件落盘，
> 会话断掉可恢复；选择题交互复用 CLI 自带的提问机制，白板不建表单。

## 1. 需要做这个决定的原因

MVP 的澄清（旧 FR-9）是纯本地文本追加：负责人自己想出问题、手动填入，agent
不参与。实际使用暴露两个缺口：

- 负责人**提不出该提的问题**——业务盲区恰恰是自己看不见的；需要 agent 带着
  文档上下文反向拷问（同机器上 grill-me skill 的实践验证了这个方向）。
- 负责人**读不懂 agent 产出的文档**时无处可问——只能开编辑器自己啃，或离开
  白板另起会话，丢掉节点上下文。

二者都指向「在节点上发起带上下文的对话」，但方向相反，混在一个按钮里会互相
污染语义，故需裁定切分方式与配套机制。

## 2. 决定

| # | 做法 | 理由 |
| --- | --- | --- |
| 1 | 两个入口按方向切分：澄清 = agent 问人（评审动作，仅 `draft`），答疑 = 人问 agent（非评审动作，任意状态） | 一个按钮双语义无法写清任务指令；方向即语义边界 |
| 2 | 旧澄清语义**整体废弃**：手动填写入口移除，`CONTEXT.md`、BR-11、FR-9 全部改写，不留兼容入口 | 域主裁定「语义冲突直接废弃老的」；手动记问题降级为澄清对话的产物之一 |
| 3 | 可澄清类型恰为 `idea`、`prd`、`spec`、`rule`、`design`（BR-20） | 承载意图与决策的文档才有业务问题可问；reference/analysis/integration 记事实，decision 是决策的结果，work 类的歧义应回上游澄清，record/report/operation/prompt 无决策可问 |
| 4 | 提示词形态：共享骨架进代码（一次一题、至多 4 选项、推荐项首位标注 `Recommended`、自由输入、能自答不问、收尾落盘），焦点行进流程配置（每可澄清类型一行；类型集内建，缺失、越界或非法即拒绝启动）；指令与焦点行通体英文（第九轮域主裁定，与 advance 指令一致，不夹杂中文标注） | 极简可配——重心逐类型可调，骨架不给漂移空间；两处都可配是不必要的自由度 |
| 5 | 澄清进度落盘为 `.whiteboard/clarify/<文档 id>.json`，gitignore，答完一题写一次，收尾删除；再次澄清时注入恢复 | 会话寿命绑在 server 进程上（FR-21 的既有边界），长问答不可接受断了重来；JSON 因为第一读者是机器（本仓「第一读者是机器的进结构化文件」先例，见 decision-00005 §2） |
| 6 | 选择题交互复用所选 CLI 自带的提问机制（如 Claude Code 的 AskUserQuestion：至多 4 选项 + 自动附自由输入项），白板前端零改动 | 终端内已有原生渲染；白板自建表单是第二套交互通路 |
| 7 | 澄清、答疑与推进共用既有会话通道与单会话约束（FR-18），commit 粒度一会话一 commit（FR-14）（本行的「单会话约束」部分被 decision-00009 §2 第 1–2 条推翻：会话通道与 commit 粒度不变，互斥改为同目标文档 + 总数上限——原地追注） | 一条通路、无新机制；澄清进行中看不懂可直接在对话里问，互斥的实际代价小 |

## 3. 考虑过的其他选项

| 选项 | 结论与理由 |
| --- | --- |
| 一个按钮承载两个方向 | **否决**。任务指令要么写成两半互相稀释，要么靠 agent 猜用户意图；语义边界消失 |
| 保留手动填写待澄清点作为并行入口 | **否决**。同一个词两套行为，`CONTEXT.md` 无法给出单一定义；手动记录在澄清对话与编辑器里都仍可达成 |
| 每类型完整提示词全量可配 | **否决**。骨架被改坏时澄清质量无声劣化，且逐类型全文维护成本高；焦点行一行即可表达重心差异 |
| 提示词全部硬编码 | **否决**。重心不可调，域主明确要求可配置 |
| 状态文件放 `docs/` 下 | **否决**。会被 `readGraph()` 解析成节点、被自动 commit——进度是过程态不是文档 |
| 状态文件用 Markdown | **否决**。第一读者是恢复流程（机器），结构化读写 JSON 最稳；人不读它 |
| 无持久化（依赖 FR-21 的内存存续） | **否决**。server 一停即丢，逐题问答的沉没成本正是这个功能要保护的东西 |
| 白板自建选择题表单 UI | **否决**。MVP 成本高，且与终端交互并存两套通路；CLI 提问机制已覆盖 4 选项 + 推荐标注 + 自由输入 |
| plan/task/issue 纳入可澄清类型 | **否决**。work 类文档的歧义说明上游 spec/rule/prd 错了，应在上游澄清；在下游问只会把答案记错地方 |

## 4. 后果

**接受的代价**

- 澄清不再是无 agent 的轻动作：发起即占用唯一会话槽，且要等 agent 读完上下文
  才开始问。（decision-00009 后：占用的是 `max_sessions` 中的一个槽位，
  不再唯一——原地追注。）
- 骨架进代码意味着改骨架要发版；换来的是骨架不可被配置改坏。
- 状态文件是 `docs/` 之外的第二个落盘点（gitignore 内），「文件是唯一事实
  来源」的口径收窄为「**文档**事实来源唯一」——进度不是文档。
- 选择题形态依赖所选 CLI 的提问机制；不具备该机制的 CLI 降级为纯文本问答
  （骨架文字仍约束「一次一题附推荐」）。

**得到的**

- 负责人从「自己想问题」变为「回答带推荐项的具体选择题」，澄清的产出密度与
  Open Questions 的质量由骨架保底。
- 看不懂的文档在节点上就地问明白，对话结论直接落回文档并留痕。
- 会话断掉不丢已答进度，恢复成本为零。

**未经验证的前提**（落地后按真实数据看）：一是焦点行一行足以表达类型间的
重心差异，不需要更多可配置面；二是 agent 在长文档上下文下能稳定遵守「一次
一题」与落盘契约。
