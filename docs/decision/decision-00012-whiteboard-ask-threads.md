# Decision: 答疑整体改为 headless——问题即会话、只读不锁、终端答疑退役

> 答疑不再是终端会话：问题从节点浮窗或编辑器的输入框提出，agent 以
> 非交互（headless）调用在后台作答；每个问题是一个独立会话，追问以
> `--resume` 接续，问答落盘为可浏览的问题列表。答疑只读、不占文档锁、
> 不产生 commit。终端形态的答疑（`spec-00001-FR-47`）退役。全部裁决
> 均经域主逐条确认。

## 1. 需要做这个决定的原因

- 答疑今天只有一种形态：起 PTY、开内嵌终端、用户在终端里打字
  （`spec-00001-FR-47`，会话通道同 FR-11）。想在阅读文档时顺手问一个
  问题，也必须切进一个完整的终端会话。
- 域主的目标交互：在节点或编辑器旁点 Ask → 输入问题 → 收起等待 →
  回答好了再看；一个节点的问题积累成**可浏览的列表**，点开看答案、
  在该问内追问。
- 回答的呈现是硬约束：PTY 字节流带控制序列，不可直接渲染为 markdown；
  「答完了」在交互式 CLI 里只能靠等待判定（`spec-00003-FR-6`）间接读出。
- 成本疑虑已核清：交互式终端的多轮追问与 headless `--resume` 接续，
  每轮都把全部历史前缀重发给 API，计费 token 相同；差异只来自 prompt
  cache 的 TTL 命中，按前缀内容判定、与进程是否存活无关。真正贵的是
  **不 resume** 的无状态连发。headless 无成本劣势。
- 现答疑可写 `docs/`（指令明文、FR-13 边界、FR-14 一会话一 commit）。
  域主裁定：答疑是读操作——「如果是读操作，不需要锁」；改为只读后，
  文档占用（`spec-00003-FR-2`）对它就失去了保护对象。

## 2. 决定

| # | 做法 | 理由 |
| --- | --- | --- |
| 1 | 答疑走 headless：问题由白板 UI 收集，服务端以非交互（print）模式调 agent CLI，捕获其输出作为回答；不开 PTY，不开终端视图 | 回答成为可渲染的文本而非终端字节流；「答完」由进程退出定义，不再依赖等待判定 |
| 2 | **问题即会话**：每个新问题开一个独立的 agent 会话，成为该文档问题列表的一项；追问以 CLI 的会话接续能力（`--resume <session-id>`）接续**该问**的会话。不同问题可并行作答、不排队；同一问题内的追问天然串行（上一答不存在则无从追问） | 列表可浏览、话题互不污染，与域主「一堆问题、点开看答案、在该问内追问」的心智一致；整文档共一条会话则问题必须严格排队、并发 resume 会分叉。代价：每问首答重读文档（追问不重付，§4） |
| 3 | 问题列表落盘在 `.whiteboard/` 一侧（同 session history，不入 git、不产生 commit）：逐项问题、回答、时刻、所用 agent、接续标识；白板重启后列表与接续能力保持 | 问答是过程记录不是文档，落盘位置与会话转写（`spec-00001-FR-54`）同侧；文件在，白板可丢弃重建的哲学不破 |
| 4 | 答疑**只读**：headless 调用以所选 CLI 的只读约束形态发起，不得改动仓库任何文件；「按对话结论修订文档」的能力随终端答疑一并移除（域主知情认可），修订诉求走编辑器手改、推进或澄清 | 免去脏路径基线、commit 归属、无人盯屏写盘的整套风险；读写分界干净——会写的会话都有人盯着 |
| 5 | 答疑调用计入会话注册表（kind 仍为答疑）：总并发上限（`spec-00003-FR-3`）、会话面板列表（`spec-00003-FR-4`）、面板终止（`spec-00001-FR-49`）、结束通知（`spec-00004-FR-3` 通路）全部复用；但**不占目标文档**——`spec-00003-FR-2` 的文档占用对答疑 kind 排除（域主裁定：读操作不锁），同文档的答疑与推进/澄清/审计互不阻塞、同文档多问并行；等待判定（`spec-00003-FR-6`）对答疑 kind 排除——静默是思考不是等待 | 一套注册表复用可见性、上限、终止与通知；锁只保护写，读操作占锁是把轻量问答变成重操作 |
| 6 | agent 配置（`agents` 条目）增设**可选**的 headless 调用形态声明：**首调与接续两种命令形态**（`--resume` 旗标只在接续时存在，一个模板装不下两种调用）、问题占位与只读旗标；未声明的 agent 不可被答疑选用，全部未声明则无答疑入口 | headless 与只读旗标逐 CLI 不同（claude 的 `-p/--resume`、其他 CLI 各异），内建猜测必错；显式声明，能力缺失时入口如实缺失 |
| 7 | **终端答疑退役**：节点浮窗的答疑入口保留但改走 headless 形态，编辑器内的提问入口为**新增** UI；触及的既有条目（`spec-00001-FR-47`/FR-14/FR-18/FR-55 及其 AC、`spec-00003` 与 `spec-00004` 的逐会话条款、`rule-00001-BR-21`、`prd-00001` 的答疑描述）在各自修订轮改写——完整交接清单以 `spec-00005` §1 为准（域主裁定：「都应该改为 headless 形式」） | 一种能力一种形态，不设两套心智；推进/澄清/审计的终端通道原样保留，退役只及答疑 |
| 8 | 问题列表呈现为**编辑器的第三视图态**（与编辑、预览并列），槽位规则（`spec-00001-FR-31`）不动；节点会话标记不逐会话计数，激活时有终端形态会话则呈现终端、否则切到列表态；会话面板增设**逐项终止入口**（答疑无终端面板可依） | 三个「旧世界不可能」的新状态（列表占位、同文档多会话的标记、无终端的终止）各给一条不破既有规则的出路：视图态不抢槽位、不丢未保存缓冲；标记语义唯一；终止可达性（`spec-00001-FR-49`）不因形态而失守 |

## 3. 考虑过的其他选项

| 选项 | 结论与理由 |
| --- | --- |
| v1：复用等待闩锁（`spec-00003-FR-6` + OSC 777），答完通知、点开看终端重放 | **否决**（域主裁定）。回答仍是终端样式不可渲染；问答不落盘，重启即失；「答完」与「等下一问」在交互式 CLI 里是同一个信号，语义始终含混 |
| 两形态并存（终端答疑保留，headless 另设入口） | **否决**（域主裁定推翻本决定初稿）。同一能力两套心智与两套入口；「按对话结论改文档」是并存的唯一独有价值，域主认可移除 |
| 整文档共一条会话（所有问题 resume 同一条） | **否决**。问题必须严格排队（线性对话），话题互相污染，列表实为一条长对话不可浏览；同一会话并发 resume 会分叉 |
| 让 agent 自己把回答写进线程文件（指令约定格式） | **否决**。依赖 agent 服从输出格式，违约即记录损坏；服务端捕获 stdout 是机械保证 |
| 每问新开无状态调用（追问也不 resume） | **否决**。追问重付全部上下文、丢对话记忆——§1 核清的唯一真实贵法 |
| 允许 headless 调用修订文档 | **否决**。按域主自己的规则，可写就必须占锁——锁、commit 归属、无人盯屏写盘整套背回来，轻量性丢光 |
| 答疑占用文档锁（照搬 `spec-00003-FR-2`） | **否决**（域主裁定）。锁保护的是并发写，只读调用没有可保护的对象；占锁会让一个后台问题挡住推进 |

## 4. 后果

**接受的代价**

- 「答疑中让 agent 改文档」的能力消失（域主知情认可）；修订走编辑器、
  推进或澄清。
- 每个新问题的首答重新读一遍文档（独立会话）；追问不重付。同文档的
  首调指令前缀相同，prompt cache 部分缓解。
- agent 配置多一段可选声明；未声明 headless 的 agent 不可被答疑选用
  （如实缺失，不降级伪装）。
- 每次调用是一次进程冷启动（CLI 启动开销），计入「后台作答」的预期。
- 会话注册表出现第二种形态（无 PTY、无 attach、无等待判定、不占
  文档），面板与通知的呈现分支随之多一条。
- 只读的强度到旗标为止：越界写入由所选 CLI 的权限机制拒绝，白板不做
  git 回滚兜底——`spec-00001-FR-13` 的既有口径，本决定不加强它。
- 答疑调用占用总并发名额（`spec-00003-FR-3`）：并行的问题可能暂时
  挤占推进的名额——上限保护的是机器，接受。

**得到的**

- 问完即走：提问不夺走屏幕，回答异步送达，离场有通知。
- 问题列表可浏览：逐问独立、点开看答案、项内追问（resume，成本与
  终端追问等价）。
- 只读不锁：问答与推进/澄清/审计互不阻塞，同文档多问并行。
- 无新并发机制、无新通知机制、无 commit 机制卷入。

**不变的**

- 推进/澄清/审计三种会话的终端形态与全部语义（含写权限、commit、
  等待判定、终止）。
- `spec-00003` 的注册表、上限、面板与 `spec-00004` 的通知机制本身。
- 文档 status 不因答疑改变（`rule-00001-BR-21` 的这半句照旧）。

## 5. 这个决定约束什么

- `spec-00005-whiteboard-ask-threads`：全部条目在本决定的裁决之内；
  对既有文档的**完整交接清单**由其 §1 持有，本节不重复枚举。
- `spec-00001-docs-whiteboard`、`spec-00003-whiteboard-parallel-sessions`、
  `spec-00004-whiteboard-desktop-notifications`：被交接清单点名的
  条目与 AC 在各自修订轮改写（plan-00021 T2）。
- `rule-00001-docs-workflow`：BR-21 的答疑定义改写为只读问答（修订
  能力移除，`rule-00001-AC-21.3` 一并移除）——属其修订轮。
- `prd-00001-docs-whiteboard`：答疑的「按对话结论修订」描述改写为
  只读问答——属其修订轮。
- `design-00001-docs-whiteboard`：headless 执行通路、问题列表存储、
  注册表第二形态、headless 声明（含 claude 的缺省只读旗标集与接续
  标识捕获口径）——待其修订轮。
- `design-00002-whiteboard-ui`：双入口、问题列表视图、状态呈现、面板
  与通知点击分支——待其修订轮。
- 站立约束：不得为答疑另造并发、通知或 commit 通路；只读约束不得
  放宽——要写文档，回到有人盯着的会话形态；不得引入整文档共享会话
  的排队模型。
