# Decision: 等待输入判定增设显式信号通路（OSC 777 锁存）

> 细化 `decision-00009` §2 第 7 条：静默启发式保留为主判定，另采纳 claude
> CLI 自发的终端通知转义序列（OSC 777 notify）为显式等待信号，置位后
> **锁存**——空闲重绘不再把等待标志打下来。非推翻：弱语义、只驱动徽标与
> 通知的边界不变。

## 1. 需要做这个决定的原因

- issue-00020 的排查实证（node-pty 探针，两次运行）揭示：claude CLI 在
  空闲提示符并**不静默**——静默约 42s 后有插件/状态栏重绘，约 54s 后自发
  `ESC]777;notify;Claude Code;Claude is waiting for your input` 终端通知
  序列。每次重绘都把静默判定的等待标志打回去、约 10s 后再置位，标志
  true→false→true 翻摆。
- 通知层已按离场区间判重（issue-00020 修复，`spec-00004-FR-2`），但那是
  下游兜着上游：徽标与节点标记仍随标志翻摆闪动，且判重逻辑的正确性
  依赖「翻摆不是新一轮等待」这一脆弱前提。
- 黑色幽默在于：打破静默的元凶之一恰是 CLI 亲口喊的「我在等输入」——
  权威信号已经在输出流里，静默启发式却把这声喊当成「它还在干活」。
  域主裁定采纳该信号（「在 Claude Code 情况下，这个肯定要的」）。
- issue-00020 曾把「De-flap the server」以越界为由否决——那是该 issue
  自设的**本轮边界**（修复限于页面侧），不是站立约束；本决定解除的正是
  这个自设前提。`decision-00010` §5 的站立约束（不得引入推送服务或服务
  端桌面通知）不涉——信号识别发生在既有的 PTY 输出通道内。

## 2. 决定

| # | 做法 | 理由 |
| --- | --- | --- |
| 1 | **采纳 OSC 777 notify 为显式等待信号**：会话输出流中出现以 `ESC]777;notify;` 起头的序列且进程存活时，立即置位等待输入；含信号序列的输出块只置位、不触发解除（信号识别先于输出解除，spec-00003-FR-6 明文）；重复信号幂等 | CLI 亲口说的事实——实测两次运行零误报，误报面远窄于静默通路且弱语义下代价不变；序列本来就流经服务端的 PTY 通道，识别是纯增量、零新依赖 |
| 2 | **信号置位取锁存语义**：锁存期间后续输出不解除标志，仅用户向该会话的终端输入或会话结束解除；解除后静默判定照常重新武装 | CLI 说了「在等」之后，任何输出都只能是重绘噪音——它不会不经输入自行继续；锁存从源头消灭翻摆，而不是靠通知层判重兜底。输入只经白板终端到达服务端（`spec-00004-FR-2` 已依赖的既有事实），解除点天然可靠 |
| 3 | **静默启发式保留为主判定与兜底**，`decision-00009` §2 第 7 条**细化而非推翻**（原地追注） | 实测信号**慢**：静默后约 54s 才到，静默判定 10s 就置位——信号不能当主判定用（首轮提醒会迟 40 多秒）；且非 claude CLI（codex 等）不发该序列，可移植性仍靠启发式 |
| 4 | **只识别序列本身**（`ESC]777;notify;` 前缀），标题与正文不解析、不匹配 | 「Claude is waiting for your input」的措辞随 CLI 版本与语言设置变，匹配文本是脆依赖；进程存活时 CLI 发任何终端通知都意味着要用户注意，弱语义下按等待处置即可 |
| 5 | **判定的弱语义边界不变**：标记仍只驱动徽标、提示条与桌面通知，不驱动状态流转或 commit | 信号通路提高的是标志的稳定性与置信度，不改变它的职责范围 |
| 6 | **锁存解除取任一次写入**：任何按键写入该会话终端即解除，无需提交 | 简单、确定性可测；半途停手由静默通路 10s 后重新置位兜住——正在打字的人不需要被提醒，重置位恰是正确状态；提交粒度需解析回车语义，对多行粘贴与不同 CLI 脆 |
| 7 | **接受再提醒兜底的损失**：锁存消灭翻摆后，「回到页面未作答又离场」的用户对同一等待不再收到桌面通知（issue-00020 §6 的偶然兜底随翻摆一并消失） | 等待仍由徽标、节点标记与会话面板可见；长时间未作答的周期性再提醒是独立需求，另立条目排期，不借翻摆的偶然性实现 |

## 3. 考虑过的其他选项

| 选项 | 结论与理由 |
| --- | --- |
| 信号通路取代静默通路（废启发式） | **否决**。实测信号迟于静默阈值约 44s，首轮等待提醒会从 ~10s 恶化到 ~54s；且 codex 等 CLI 不发该序列，废启发式即对它们失明 |
| 匹配通知正文文本（如 `waiting for your input`） | **否决**。措辞是 CLI 的实现细节，版本升级或本地化即失配；序列前缀是协议层约定，稳得多 |
| 静默判定收到空闲重绘不解除（识别重绘） | **否决**。无法通用地区分「重绘」与「真产出」——等价于给每种 CLI 建输出白名单，脆且无底 |
| 解析 OSC 9 等其他终端通知约定 | **搁置**。未在实测中出现，无实证不立条目；留 `spec-00003` §6 待有实证再议 |
| 锁存解除取一次提交（回车为界） | **否决**。需解析提交语义，对多行粘贴与不同 CLI 的按键约定脆；任一次写入 + 静默通路重新置位已覆盖「半途停手仍在等」的情形 |
| 页面侧按「回来又离场」重发一条（改 `spec-00004`） | **否决**（域主裁定）。与「一次等待别反复提醒」的既有诉求（issue-00020）有张力；长时间未作答的周期性再提醒是独立需求，另立条目 |
| 不做（维持纯静默判定 + 通知层判重） | **否决**。徽标与节点标记仍随翻摆闪动；判重的正确性依赖「翻摆非新等待」的前提，上游修正比下游兜底便宜且治本 |

## 4. 后果

**接受的代价**

- 锁存引入一个例外情形：若 CLI 发出通知后**不经用户输入**自行继续（如
  定时钩子触发续跑），标志会错误地保持到下次输入或结束——弱语义下代价
  是徽标多亮一阵，接受。
- 会话输出内容本身携带真实 OSC 777 字节时（如在会话里跑探针脚本、`cat`
  含该序列的夹具）会被误判为等待并锁存——只匹配前缀无法区分，弱语义下
  接受。
- 锁存消灭翻摆的同时，删掉了 issue-00020 §6 明写保留的兜底：「回到页面
  未作答又离场」的用户不再因标志翻摆而被再提醒一次，桌面通知未实际显示
  时也失去自然重发机会——域主裁定接受（§2 第 7 条），周期性再提醒另立
  条目。
- 对 `ESC]777;notify;` 前缀形态的依赖：CLI 换用其他通知约定时信号通路
  失效——行为退回纯静默判定（现行），不会更坏。

**得到的**

- 对发该序列的 CLI（claude），等待标志在真等待期间不再翻摆：徽标、节点
  标记停止闪动；`spec-00004-FR-2` 的离场区间判重对其从「兜住翻摆」变成
  「几乎无翻摆可兜」。不发该序列的 CLI（codex 等）行为照旧，判重仍在
  兜底。
- CLI 亲口确认的等待获得权威置位，误报只剩静默通路的首轮窗口。

**不变的**

- 静默阈值（量级 10s，实现常数）与其主判定地位。
- 等待输入的弱语义与职责边界（只驱动徽标与通知）。
- 服务端零新依赖、零新配置键；`decision-00010` §5 的零推送约束不涉。

## 5. 这个决定约束什么

- `spec-00003-whiteboard-parallel-sessions`：FR-6 改写为双通路 + 锁存
  （第十八轮修订轮承载），AC-6.6 … AC-6.13 新增。
- `spec-00004-whiteboard-desktop-notifications`：FR-2 括注的翻摆前提
  收窄为「信号到达前的窗口，以及不发该序列的 CLI」，判重语义不变——
  **离场区间判重不得因信号通路移除**（AC-2.6 仍可达：实测信号到达前的
  插件行重绘仍造成翻摆）；括注的原地校正列入 `spec-00004` 自己的后续
  修订轮，不在本轮就地改。
- `design-00001-docs-whiteboard`：会话通道一节增补信号识别（含跨输出块
  的序列缓冲）与锁存状态机（修订由 plan 轮列为任务）。
- `CONTEXT.md`：「等待输入」词条扩义为双通路（随 spec 接收同步）。
- 原地追注：`decision-00009` §2 第 7 条（细化注记）。
- 站立约束：信号通路只增不替——静默启发式不得因此移除；标题正文不得
  进入匹配条件。
