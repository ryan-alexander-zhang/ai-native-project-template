# Decision: Markdown 即 DSL——文法成文、校验三处复用，不立第二事实来源

> 条目解析的加固路径裁定为：现行写作约定升格为**正式条目文法**（宿主仍是
> Markdown），一份校验器三处复用（白板解析诊断、仓库契约测试、agent 会话
> 产出校验），解析器由行级正则升级为 remark AST。外链 DSL 文件**否决**；
> 同文档围栏结构块**暂缓**，保留为退路并写明触发条件。

## 1. 需要做这个决定的原因

白板第四轮起解析文档正文（decision-00004），「写法即契约」的代价当时已明认：
写法漂移或约定与解析脱节，读数就出错。第四、五轮之间它相继暴露两起，都被
抓到但都**不是被解析器抓到的**：

| 事故 | 后果 | 被谁抓到 · 证据 |
| --- | --- | --- |
| record-00001 的区间行（九条 AC 挤一格，README 从未许可的简写） | BR-2…BR-9 共 8 条误报未覆盖（严格口径；decision-00004 §1 报的 7 条是宽口径 grep，二者口径不同不矛盾） | plan-00005 实施 agent 逐行核对；record-00001:117 展开注记、record-00004 实测注记 |
| record 的细粒度 `verifies`（README 明文许可的写法） | 三条合法引用被图模型当**断链**，白板长期显示「3 issues」 | issue-00005 §8 记为残留，decision-00004 §5 裁定一修正 |

同时，域主提出的三项诉求成立：约束 agent 的文档输出、白板消费更格式化、用
固定代码校验。分歧只在**用什么架构拿到它们**。

## 2. 决定

四条，按解决的问题分开：

| # | 做法 | 解决 |
| --- | --- | --- |
| 1 | **文法成文**：spec/rule/record 三个文件夹 README 各自新增「机器可读形态」小节，精确到行形态（列表项/决策表行/归属标注/验收行表头，禁止区间与多 id 行）——这就是 DSL，宿主是 Markdown | 契约此前散落在解析器的正则里，写作者看不见 |
| 2 | **解析诊断**：识别「疑似条目而不合文法」的行，连同既有「无法归属」并入一个显性诊断清单，白板呈现并计数（`spec-00001-FR-40`） | 漂移从无声漏读变成当场报警 |
| 3 | **一份校验器三处复用**：白板加载/刷新即诊断；仓库契约测试「本仓 `docs/` 全量零诊断」进测试套件当门禁；推进会话的任务指令携带文法要求、会话产出扩展校验（`FR-41`，沿 FR-17 的既有钩子） | 「用脚本限制 agent 输出」「固定代码校验」两项诉求 |
| 4 | **解析器正则 → remark AST**：行为契约不变，483 条既有测试为回归护栏；AST 的位置信息供诊断定位到行 | 对空格、粗体嵌套、表格对齐的容错从根上变好 |

分界原则（本仓已有先例）：**第一读者是机器的进结构化文件**（流程配置在
`whiteboard.config.yaml`），**第一读者是人与评审的留在 Markdown**（EARS 句式
与 GWT 的价值恰在可直接读）；嵌在 Markdown 里的 DSL 有 mermaid 先例。

## 3. 考虑过的其他选项

| 选项 | 结论与理由 |
| --- | --- |
| **外链 DSL 文件**（Markdown link 一个 JSON/YAML，FR/AC/BR 结构入内） | **否决**。事实来源变成两个——散文在 md、结构在 json，漂移从「格式漂移」升级为「两个文件互相说谎」，恰是 DSL 想消灭的东西；评审跨文件对照，spec 正文变空壳；违反仓库「文件是唯一事实来源、一题一文」的立身原则。JSON 也不消灭漂移（不合 schema 的 JSON 一样写得出来），它的真优势是校验响度——本决定第 2、3 条以更低代价拿到同一响度 |
| **同文档围栏结构块**（\`\`\`yaml 条目块写在 spec 正文内，mermaid 同型） | **暂缓，留作退路**。单一事实来源保住、schema 校验直接，但 spec-00001 与 rule-00001 需全量改写，GWT 进 YAML 字段后散文评审体验降档。**触发条件（可操作口径）**：本决定落地后，连续三个 plan 轮次每轮都有真实（非夹具）诊断进入 record 观察项——即文法+诊断没能止住漂移——再评估迁移，届时先做成本表 |
| **从 md 单向导出 JSON 供外部工具** | 与本决定不冲突，属将来需求出现时的生成物方向（md 仍是唯一源）；当下无消费者，不做 |
| **维持现状（正则 + 运行时无法归属区）** | 两次事故证明响度不够：无法归属只接住「id 存在性」断裂，接不住形态残缺（区间行恰好整行不被识别，于是无声） |

## 4. 后果

**接受的代价**

- 文法一旦成文即是承诺：README 的形态规则、解析器、诊断启发式三者必须同步
  演进——文法改一处要动三处。这换来的是契约第一次对写作者可见。
- 诊断的启发式（「疑似条目」的判定）有假阳性风险：正文散文里粗体书写一个完整
  条目 id 会被盯上。约定即口径：条目 id 在散文中一律用反引号（本仓现状已然），
  粗体 id 是声明专用形态。
- agent 任务指令变长（多一段文法要求）。
- remark AST 引入一个真实依赖（本仓前端已用 remark 系渲染，服务端新增同源
  依赖，不算新面孔）。
- **诊断不豁免 `draft` 文档**：半途手写的不合式草稿会让契约测试变红——这正是
  门禁的本意（写作期以白板诊断区为即时反馈，契约测试守收尾），接受这个工作流
  代价，不为 draft 开口子。

**得到的**

- 域主三项诉求全部落地且事实来源仍是一个。
- 区间行一类事故的发现成本从「一次审计」降为「一次刷新」。
- 契约测试把「本仓文档全量合文法」变成每次 `npm test` 的常绿断言。

**未经验证的前提**（落地后按真实数据看）：一是诊断启发式在本仓全量文档上
假阳性为零；二是任务指令加长后 agent 产出质量不劣化。
