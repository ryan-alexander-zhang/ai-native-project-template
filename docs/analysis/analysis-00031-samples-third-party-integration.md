# S7 调用外部三方应用（防腐层 + 出站/回调 + 对账）

对应 sample：`aipersimmon-ddd-samples/s07-third-party-integration`（两个模块：`payment-service` 是我们的，
`gateway-stub` 是那家我们管不着的支付网关）。场景清单见 [[analysis-00014-ddd-samples-scenario-catalog]]。

## 0. 本篇定位

S4 是两个我们自己的服务经 broker 通信，S6 是两个我们自己的服务同步通信，S5 是消费一个上游的消息。
本篇的对方**不属于我们**：它有自己的词汇、自己的可用性、自己的重发策略，并且不会为我们改任何东西。

一句话概括本篇：**每一条通道都是 at-least-once，每一个写入方都必须幂等；而当没有答案时，唯一正确的
自动动作是交给人。**

三条通道，缺一不可：

| 通道 | 方向 | 谁触发 | 没有它会怎样 |
| --- | --- | --- | --- |
| 出站请求 | 我们 → 三方 | 命令提交后由中继发出 | 崩在"用户点了付款"与"网关知道"之间就永久丢失 |
| 回调 | 三方 → 我们 | 网关，best-effort | 拿不到结果 |
| **对账拉取** | 我们 → 三方 | 定时轮询 | **回调丢一次，那笔钱永远悬着** |

第三条是 catalogue 明确要求的，也是真实项目最常省掉的一条——因为在测试环境里回调总是会到。

## 1. 出站：为什么不在 handler 里打这个 HTTP

`RequestPaymentHandler` 里没有任何网络调用。它存意图（聚合行）+ 存一条 outbox 行，同一个事务，然后返回。
把 `gateway.charge(...)` 写在 handler 末尾有三种错法，每一种都对应一类真实事故：

1. **事务开着等网络。** 一条数据库连接被一个"对方的运维决定"占着。网关慢一个早上，连接池被抽干，垮掉的
   是与支付无关的接口。（S6 把同步调用放进 precheck 就是为了这个；本篇更进一步，放到提交**之后**。）
2. **这个调用回滚不了。** 它之后有任何失败，事务撤销的是行、不是那笔扣款——钱走了，本地没有记录。
3. **让客户等对方。** 结果本来就是异步的，等只买到一个更长的超时窗口。

## 2. 出站为什么走库的 outbox，以及它的三个代价

`ChargeRequested` 是一个 `@Externalized("gateway:charges")` 的集成事件，destination 不是 topic，而是本应用
自己的 `EventDestinations` 产出、自己的 `OutboxDispatcher` 认识的一个路由键。库只要求 destination 在**写入
事务里**解析好并存在行上。

这样换来的东西全部不用自己写：与聚合同事务提交的行、租约（两个实例不会同时发同一行）、退避重试、
超次进死信。这些都不是 broker 特有的——它们正是一次出站付款请求需要的东西。

代价三条，都写在 `ChargeRequested` 与 `ChargeRequestOutboxDispatcher` 的 javadoc 里：

- **一个应用只有一个 `OutboxDispatcher`。** 中继注入一个，
  `AipersimmonDddOutboxAutoConfiguration` 里的每个默认实现都 `@ConditionalOnMissingBean` 让位。所以自己
  定义这个 bean 就**顺手拆掉了 LOCAL 事件的进程内投递**，而且没有任何提示——中继只要 `dispatch` 正常返回
  就标记已发送。库的 javadoc 自己给了做法（"define your own OutboxDispatcher bean that composes the
  others"），本 sample 就是那么组合的，并且用一个 LOCAL 事件的测试证明那条腿真的接着（见 §9 控制 4）。
- **中继是快递员，不是翻译。** 三方 202 里的 `txn_ref` 被记录后**丢弃**。要把它写进聚合，就得在一个即将
  被标记已发送的传输适配器里做聚合状态变更——在任何命令之外，也就在校验、拦截器链和操作日志之外。答案只
  能从回调或拉取回来，而那两条都过命令总线。
- **因此三方的契约得配合。** 本 sample 的网关同步只回 202，业务信息为零，所以丢掉它不损失什么。**同步就
  给出决定的网关（很多是这样）不适合这条管道**：走 outbox 就等于放弃一个已经拿到的答案去等 webhook，代价
  是延迟，以及"卡被拒"这件事晚一个往返才知道。这是一个真实的取舍，另一边是自己的任务表 + worker（能同时
  写下尝试与答案）。

## 3. 幂等键：为什么是 payment id，以及两种失败的区别

`PaymentId` 既是聚合身份，也是发给网关的 `Idempotency-Key`。它必须在**发出第一次之前**就存在，所以由命令
处理器用框架的 `IdGenerator` 铸出，而不是数据库插入时生成——事后才知道的键保护不了那次调用。

这里有一个我最初写错的区分，负向对照把它逼出来了（详见 §9 控制 1）：

| 失败形态 | 钱动了吗 | 换键重试会怎样 |
| --- | --- | --- |
| 请求还没落地就 503（`FAIL_FIRST_CHARGE`） | 没有 | 也只扣一次——**这个用例证明不了幂等键** |
| 已经扣款、响应丢了（`LOSE_FIRST_RESPONSE`） | 动了 | **扣两次**（实测 `chargesCreated` = 2） |

所以"我们收到了错误，说明什么都没发生"永远不是对远程调用的安全解读，而**能证明幂等键的只有第二种用例**。
stub 为此专门加了 `LOSE_FIRST_RESPONSE` 模式。

## 4. 入站：三层护栏与"传输重放 ≠ 业务重复"

回调端点是公网上一个**不带认证的 POST**。库的 `ReplayProtectionFilter` 提供三件事：验签、时间窗、nonce
去重。边界存储用 `aipersimmon-ddd-web-store-jdbc`——这是 samples 里"一律 MyBatis-Plus"的那条唯一例外
（库只有 jdbc 与 redis 两种边界存储实现），S2 取 redis，本篇取 jdbc，两种就都覆盖到了。它不需要额外
基础设施，代价是要跑 schema 校验器和一个保留期清理调度（redis 靠 TTL）。

**最要紧的一条区分：签名与 nonce 拦得住"同样的字节再发一遍"，拦不住"同一个结果重新签一遍再发"。**
网关每次通知都换新的 `event_id`、新 nonce、新签名，所以两条"扣款成功"的字节完全不同，两条都是真的，
replay guard 放它们过去是**对的**。去重是聚合的事，任何边界过滤器都做不到。

`event_id` 也不能当去重键：它每次发送都是新的。真正去重的是聚合的状态。

配置上踩到的两件（都在 yaml 里注明）：

- `signature-header`/`timestamp-header` 在 `replay` 下，nonce 的头在 `replay.nonce` 下。改了前两个、忘了
  第三个，每一个真回调都会因为**头检查**（"Missing nonce"）而 401——一个长得和攻击一模一样、其实全是我方
  配置的失败。
- `nonce.enabled=false` 曾经不像它读起来那样只是"少一层保护"：滤器只在开关打开时读 nonce 头，于是把
  nonce 签进规范串的方案（正是本库推荐的那种）会**全量验签失败**，而且报的是 "Invalid signature"。
  [[issue-00162-nonce-dedup-off-makes-a-nonce-bound-signature-unverifiable]] **已修**：头无条件读，去重仍按
  开关走。**用本篇的对照 3 验收**：同样关掉这个开关，修复前 7 红（6 条是合法回调被拒），修复后**恰好 1 红**
  且是那条关于重放的。现在关掉去重的代价就是去重。

## 5. 乱序：比较状态，不比较时间

webhook 投递没有顺序保证：相差一毫秒发出的两条通知可以任意顺序到达，旧通知的重投也可以在新通知之后到达。
聚合因此**既不信到达顺序，也不信发送方的时间戳**（那是对方的时钟，而且重投带的是原始发送时间）。

它信的是这些状态只会前进：`REQUESTED(0) → SUBMITTED(1) → SUCCEEDED/FAILED(2)`。比 rank 就把"这两条哪个更
新"变成了一个关于状态本身的问题。一条落后的通知返回 `SUPERSEDED`，什么都不改——但**仍然补上 `gateway_ref`**
（迟到的 `ACCEPTED` 对状态是旧的，对身份仍然是对的）。

注意 `PaymentStatus` 里**没有**"不知道"这一档。不知道不是付款的状态，是我们信息的状态，建模成聚合上的
`review_reason`，于是状态还能被后来终于到达的回调结算。

## 6. 矛盾、不可解释、以及一律 2xx

三种"没法自动处理"的输入，处置一致：**接受（2xx）、保留已知的事实、叫人**。

| 输入 | 为什么不能自动决定 | 做什么 |
| --- | --- | --- |
| 先成功后失败（同一笔两个终态） | 没有规则能在"扣了"与"拒了"之间选对：一边白送货，一边拒收付了钱的客户 | 保留第一个 + 打标 |
| 不认识的 result code | "未知即失败"是这类集成能写下的最贵一行代码：网关哪天为某种新的**成功**加一个码，每一笔都会被记成失败，而被扣了钱的客户正是会来投诉的那批 | 不结算 + 打标 |
| 说的是我们没有的 payment | 回调 URL 与另一个环境共用，或这条通知是别人的交易 | **404**，因为这是要人看的配置错误；且此处不存在竞态——出站请求只在聚合行提交之后才离开本服务 |

前两种为什么是 2xx：网关**一直重发直到成功**，而重发不会产生一个我们能读懂的码。回 4xx 只是要求再被
告知一次。`SettlementOutcome` 的四个值里没有一个是异常，正是这个意思。

## 7. 悬挂态与对账通道，以及我在这里犯的错

对账轮次的形状与 S11 的清扫完全一致：候选扫描（advisory）→ 每个 id 一条命令 → 一份可读的 report。
两个关键设计：

- **不需要租约。** S11 的 javadoc 说过没有 version 可仲裁的工作（"call a partner API"）需要先 claim。
  本轮次不需要，因为它在三方那边做的是**查询**：两个实例问同一个问题得到同一个答案，只多付一次请求；
  随后的写是带 version 的状态迁移，一个赢一个被拒。**一旦这个轮次开始重发扣款，就必须要 claim**——还得
  加上幂等键。
- **同一条命令，两条来路。** 回调与对账产出的是同一个 `RecordGatewayResult`，只有 `channel()` 不同。
  两套结算路径就是同一条规则的两个实现，而有 bug 的永远是跑得少的那个。

**我最初写错的地方**：`NoRecord`（三方 404）立刻升级为人工。用两个调度器真跑一遍就翻车了——对账定时器比
中继定时器早 13 毫秒，于是它问的是一笔**自己还没发出去**的付款，网关当然没记录，于是打标；而**打标是粘性
的**（扫描排除已打标的行），这笔付款从此永远不再被扫到，永远停在 `REQUESTED`。

修法不是把测试放宽，而是改设计：**对"缺席"要有耐心。** 两种"不知道"的答案（还在 pending、完全没记录）
都压到 `give-up-after` 之后才升级，之前只计一个 `awaiting` 计数。由此还得到一条配置约束，写进了 yaml：
**`stale-after` 有下界——必须大于出站通道送达一次请求所需的时间**，否则每一轮都在问三方还不知道的付款。

`ReconciliationReport` 因此把 `awaiting` 与 `unreachable` 分开计：一个等就好，一个要重试；一轮里
`awaiting` 占多数，说明对账跑得比出站快，是配置问题而不是支付问题。

## 8. 分层：防腐层是一个包，并且是**密封**的

`payments/infrastructure/gateway` 里放了两个方向的全部：HTTP 客户端、出站 dispatcher、四个 wire record、
code 表、验签实现、**以及回调 controller**。包内每一个类型都是 package-private，所以"哪些类知道 `51` 是
拒付"由编译器回答，不靠 review 记性。

**回调 controller 不在 `interfaces`，这是本 sample 与其他 samples 唯一的布局分歧**，理由写在
`GatewayCallbackController` 的 javadoc 里：回调端点不是我们的 API，是一次出站调用的返回路径——它的 URL、
认证方案、载荷、重发行为全部由对方规定，换一家供应商它不是被修改而是**消失**。那是适配器的定义。放在这里
才能让两个方向共用同一张 code 表，而那张表是最不该漂移的东西。

三条 ArchUnit 规则钉住这个边界：库的全套规则、"包外任何类不得依赖这个包"、"包内任何类型不得 public"。

## 9. 负向对照（八个，逐个单独跑，全部实测）

规则：一次只改一处，跑完恢复，确认红的是**预期的那些**。

| # | 改动 | 预期 | 实测 |
| --- | --- | --- | --- |
| 1 | `Idempotency-Key` 换成每次新 UUID | 双扣 | `LOSE_FIRST_RESPONSE` 下 `chargesCreated` 2（期望 1），共 3 红。**并且这一轮改出了 sample 自己的问题**：原来的用例用 `FAIL_FIRST_CHARGE`（扣款前失败），换键也只扣一次，所以它的名字过度声明了——加了 `LOSE_FIRST_RESPONSE` 模式与一个新用例 |
| 2 | 去掉 `status.supersedes(notified)` 判断 | 乱序回退 | 恰好 2 红（手投与三方驱动各一） |
| 3 | `nonce.enabled=false` | 重放放行 | 当时 7 红。只有 1 个关于重放，另外 6 个是**合法回调被拒**——这一条查出了 [[issue-00162-nonce-dedup-off-makes-a-nonce-bound-signature-unverifiable]]。**修复后重跑同一对照：恰好 1 红**，即预期的那条 |
| 4 | dispatcher 的进程内腿换成空实现 | LOCAL 事件无声丢失 | 恰好 1 红，且行仍被标记已发送——无异常、无死信 |
| 5 | 删掉 `GatewayFailureClassifier` 的 `@Component` | 400 被当可重试 | 恰好 1 红（一次轮询后死信 0） |
| 6 | 扫描去掉 `review_reason IS NULL` | 同一告警每轮重放 | 恰好 1 红 |
| 7 | code 表 `default` 改成 `FAILED` | 未知即失败 | 恰好 3 红——回调、三方驱动、拉取各一，正好证明这条规则在**三条来路上都生效** |
| 8 | `NoRecord` 立即升级 | 未发出的付款被永久打标 | 2 红：定向用例 + 双调度器的端到端用例 |

没有重复做的一条：**删掉 `RequestSignatureVerifier` bean**（滤器 `@ConditionalOnBean` 于它，不存在就
放行一切未签名请求）。S2 已经实测过，本篇不重复。

## 10. 没做的事

| | |
| --- | --- |
| 死信重放成一次新的出站尝试 | 库有 `DeadLetters` 端口，重放是运维动作，本 sample 只做到"死信 + 对账会发现它" |
| 退款/撤销 | 反向资金流是另一条业务流程，不是本篇的续集 |
| 多币种 | 币种来自配置；多币种部署应把它放到聚合上 |
| 熔断、隔仓、共享重试预算 | 与 S6 同一个结论：属于 resilience 库或 mesh |
| 三方沙箱 | stub 就是自包含的答案，且它能做真沙箱做不到的事（丢响应、乱序、矛盾终态） |
| 两个模块一起启动的端到端 | 与 S4/S21/S6 同一个缺口；本篇的 stub 在测试 JVM 内，另可 `java -jar` 手动跑 |
