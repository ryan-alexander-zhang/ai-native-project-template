# S21 事件契约演进与多版本共存

对应 sample：`aipersimmon-ddd-samples/s21-event-contract-evolution`（两个服务模块）。
场景清单见 [analysis-00014-ddd-samples-scenario-catalog](analysis-00014-ddd-samples-scenario-catalog.md)，上游链路见
[analysis-00025-samples-integration-events-across-services](analysis-00025-samples-integration-events-across-services.md)。

## 0. 本篇定位

事件一旦发出就是公共契约：**发不回来**，而线上那些记录会活得比产出它们的代码更久。所以真正要回答的不是
"怎么改字段"，而是**发布方与消费方处于不同版次的那段时间**（滚动发布是几小时，实际常常是几个月）怎么活
下去。

S4 已经钉过一条：未登记的版本进死信。本篇把它变成可存活的，并且把三件最容易翻车的事做成测试——**积压行
带着旧版次继续发**、**双发一个事实等于生效两次**、**只删 upcaster 会静默丢消息**。

## 1. 三种变更，三条路

sample 里的契约有真实履历：

| 版次 | 形状 | 变更性质 |
| --- | --- | --- |
| v1 | `orderId, customerId, sku, quantity` | — |
| v2 | `orderId, customerId, lines[]` | **重构**。单字段变列表，没法伪装成可选字段，所以版次必须动；但能从 v1 无损推导，所以消费方可以被机械地搬过去 |
| v3 | `…, warehouseCode` | **新信息**。从任何旧版次都推不出来，所以这个字段的**"缺失"本身必须有含义** |

**"需要升版次"和"能被 upcast"是两个独立问题。** v2 两个都是 yes，v3 只有第一个是 yes。

还有第三种，也是**最该优先走的一条**：

| 变更 | 要不要升版次 |
| --- | --- |
| 纯加一个可选字段 | **不用**。旧消费方忽略未知 JSON 属性,照跑（`anOptionalAdditionInsideOneRevisionNeedsNoBump`） |
| 重命名/拆分/改结构 | 要。再"可选"也不是 additive |
| 加一个消费方必须读到的字段 | 要，且后继版次必须容忍它缺失（见 §3） |
| 删字段 | 要，而且**这一条 upcast 救不了**：消费方要的信息消失了,只能等它先不再读 |

## 2. 谁持有哪些版次：这才是不能共享 jar 的真正原因

| | 树里有 | 为什么 |
| --- | --- | --- |
| 发布方 | **只有 v3** | 它只发一个版次。留着旧类＝留着发旧版次的能力,而这正是契约所有者在迁移期最不该有的东西（§5） |
| 消费方 | **v1 + v2 + v3** ＋两个 upcaster | 所有**还可能到达**的版次 |

S4 说过共享契约 jar 会带回编译期耦合。到这里理由变得更硬：**jar 一次只有一个版本,它根本表达不了"两边
处于不同版次"**，而那恰好是发布期间的常态。两个树的形状不一样,不是疏忽,是事实。

测试把这条钉成可验证的：发布方的 `IntegrationEventCatalog`（扫描自己的事件类得来）只有 v3 一条,消费方
有三条。两份普查都没错,任何单一 artifact 都当不了两者。

## 3. upcaster 链，与那条铁律

`OrderContractUpcasters` 两跳：v1→v2（一条线变成单元素列表,精确无损）、v2→v3（`warehouseCode` 留 null）。
一个 listener,只认 v3。

**买到了什么**：没有 upcaster 的话,多版本共存＝**每个历史版次一个 listener 方法,每个消费方一份,永远**——
而版次只会变多。链把这笔成本挪到边界：每个退役版次一个 upcaster,底下的用例写一次。

**铁律：旧版次没携带的信息,upcast 不得凭空编造。** 库自己的 javadoc 就是这么写的（`EventUpcaster`：
"What the old revision never carried, the upcast must not invent"）。所以：

- v2→v3 留 null；
- "null 是什么意思"由**消费方**在 `OrderPlacedListener` 里一个具名常量决定,摆在明面上；
- 推论：**一个加了消费方必读字段的后继版次,必须是能容忍缺失的版次**（nullable 或契约上写明默认值）。如果
  新字段无法缺失,诚实的选项是新的逻辑事件、或一次硬切,不是一个塞了合理猜测的 upcaster。

### 3.1 负向对照告诉了我一件更难看的事

把 v2→v3 改成编造 `"MAIN"`,**只有一条断言变红,其余七条全绿**——因为编造的值恰好等于 adapter 本来会用的
规则,**效果完全一样**。

结论：**效果目前区分不出来的契约违约,仍然是违约**。它会在规则改变的那天冒出来,冒在几年前写下的数据里。
能抓住它的只有**对 payload 断言**,这就是那个记录 envelope 的 listener 存在的理由——不是为了好看。

### 3.2 归一化之后，线上版次对应用不可见

`envelope.version()` 描述的是**它手里那个 payload 的版次**（upcast 后＝3),线上原始版次留在 Kafka 记录的
header 上,应用拿不到（`KafkaIntegrationEventListener:220-224`）。

这是故意的,而且是对的：**一个按线上版次分支的消费方等于把刚买的归一化退了货**,又把 per-revision 代码请
回来了。真要区分,就得让 payload 自己带信息——而"把字段留空"正是这件事。

## 4. 什么机制都抓不住的一种变更

形状不变、**含义变了**：`quantity` 从"件"变成"箱",`status` 多了一个取值,金额从含税变成不含税。

没有版次会动,没有 upcaster 会跑,没有死信会响。库能校验的是 `(name, version)` 与形状,含义在它的视野之外。
唯一的办法是**把它当不兼容变更处理**——升版次,让旧消费方在死信里看见,而不是在报表里看见。这条只能靠纪律,
sample 不能给你一个测试。

## 5. 双发：看起来是照顾旧消费方，实际是重复生效

迁移期"同时发 v1 和 v2,让旧消费方还能用"是个常见提议。`dualPublishingOneFactAppliesItTwice` 把它做了一遍：
同一个订单,一条 v1、一条 v3,**预留了两次**。

inbox 救不了：去重键是 `(source, id)`,而这是**两个不同的事件**——重复在发布决策里,不在传输里。而且受害
者恰好是双发想保护的那批消费方：还登记着旧版次的那些。

所以发布方的规则是一句话：**一个事实,线上一个版次。** 兼容性由消费侧的 upcast 承担,不由发布侧的重复承担。

## 6. topic 与版次

路由表按 `(name, version)` 键,所以**一个版次可以搬到新 topic**。sample 的默认是三个版次同一个 topic
（发布方的 yaml 里写了理由：一 topic 一版次会让每个消费方要多持有一份订阅,而 `(name, version)` 已经告诉
了它手里是哪个版次）。

消费侧保留了一个 legacy topic,把搬迁的机械动作演示完整：

- **订阅集＝已声明的各版次所点名的 topic 的并集**（`theSubscriptionIsTheUnionOfTheTopicsTheDeclaredRevisionsName`）。
  没有任何配置说"读两个",是注解说的。
- 于是**退役版次的 `@Externalized` 不能删**：删了就不再订阅旧 topic,而"没人订阅的 topic"什么都不报——
  又是一条静默失效。
- 顺带一笔运维账：**订阅两个 topic 就欠两个 `<topic>.DLT`**。缺一个,那个分区上的毒丸会原地无限重试。

## 7. 与数据库迁移的顺序

sample 的 `V1__inventory.sql` 里写了这条：**schema 先,契约后**。

消费方的表可以在任何事件携带 warehouse 之前就先能存 warehouse；反过来不行——**如果一个消费方的 schema 和
它的契约在同一次发布里同时学会这个字段,它就没有"可以先上线"的窗口**,而 §8 的部署顺序正是建立在那个窗口上
的。迁移本身的机制归 S23。

## 8. 部署顺序：消费方先

`arevisionThisConsumerHasNotAdoptedIsDeadLetteredRatherThanGuessedAt` 就是"发布方先上"从消费侧看到的样子：
一个没有本地类的版次,当场死信。解析是精确的 `(name, version)` 对且没有跨版本回退——这是**对的**默认,因为
按错误版次读 payload 是**静默误解**,比大声拒绝坏得多。

于是顺序是死的：**先让每个消费方认识新版次,等它到生产,再让发布方开始发。** 消费方提前认识 v4 的代价是零
（v3 还在发,它照读）；发布方提前发 v4 的代价是每个订单一条死信。

## 9. v1 什么时候可以删

两步,而且第二步的两个做法一个响一个不响。

**第一步：确定"最后一条 v1 记录已经被读掉"。** 它不等于 topic 保留期,而是

```
max(topic 保留期, 发布方 outbox 积压排空, 死信重放窗口)
```

中间那一项是本篇钉出来的：`abacklogRowShipsAtTheRevisionItWasWrittenAt`——outbox 行的 payload、version、
destination 都是在**发布事务里**定下并存在行上的,relay 只是个快递员,不是翻译。所以**把版次从发布方删掉
并不会让它停止被发布,排空才会**。而这一项对消费方是不可见的,只能被告知。

**第二步：删。两种删法不一样。**

| 删法 | v1 记录的结局 |
| --- | --- |
| 删**类** | `(name, version)` 无法解析 → **死信**。响、可计数、可重放 |
| 只删 **upcaster**,留着类 | 解析成一个没有任何 handler 的类 → **在 inbox 之前被跳过**。无效果、无 inbox 行、无异常、无死信、无消费延迟 |

`SilentSkipWhenTheUpcasterIsGoneTest` 就为这一条存在（也是 `upcasters-removed` profile 唯一的用途）。
**删 upcaster 感觉像是清理里更安全的那一半,它是会丢订单的那一半。**

那个跳过本身是值得有的（订阅了繁忙 topic 的服务不该为每条不关心的记录写一行 inbox）,所以 sample **没有**
为了让隐患消失而把 `skip-locally-unhandled` 关掉——关掉才是把它藏起来。

所以删除只有两个合法状态：**类和 upcaster 一起留**（旧记录被正常升级）,或者**一起删**（旧记录死信,响）。
"留着类、删掉 upcaster"是唯一不该出现的中间态,而它恰好是分两次提交做这件事的人自然会经过的那一步。

## 10. 契约测试放在哪一侧

本篇的答案是"两侧各一份,对着 wire,不共享代码"：

- 发布侧断言**它写到 topic 上的东西**（`ce_type`、`ce_dataschemaversion`、payload 形状）——用裸
  `KafkaConsumer` 读,因为要验的是外部消费者看到的东西；
- 消费侧断言**它能读什么**,记录由测试自己造。造记录而不是启动发布方是刻意的：两个服务之间的契约就是 wire
  格式,而且测试能造出任何活着的发布方都造不出来的版次——**那正是迁移期消费方必须活下来的输入**。

共享一个契约测试 jar 会把 §2 的耦合从生产代码搬到测试代码里,换来的"一致性"是假的：两侧本来就不该一致。

## 11. 常见错法

| 错法 | 后果 |
| --- | --- |
| 加可选字段也升版次 | 白给自己一条 upcaster 和一次协调发布 |
| 重命名字段但不升版次 | 旧消费方读到两个字段都缺失,**静默什么也不预留** |
| 发布方先上新版次 | 消费方每个订单一条死信,直到它跟上 |
| 迁移期双发两个版次 | **同一事实生效两次**,inbox 救不了,受害者正是要保护的旧消费方 |
| upcast 里填一个"显然的默认值" | 伪造值与真实值下游无法区分；规则改变那天,几年前的数据一起错 |
| 后继版次的新字段不可缺失 | upcast 无解,只能新事件或硬切 |
| 消费方按线上版次分支 | 归一化白买了,per-revision 代码回来了（而且库故意不给你线上版次） |
| 只删 upcaster、留着退役类 | **旧记录静默消失**,无任何信号 |
| 退役版次删掉 `@Externalized` | 静默不再订阅旧 topic |
| 搬了 topic 却只建一个 `.DLT` | 缺 DLT 的那个分区上,毒丸原地无限重试 |
| 只按 topic 保留期决定何时删 v1 | 忽略发布方积压与死信重放窗口 |
| 形状不变、含义变了 | 没有任何机制会报——只能靠纪律当不兼容变更处理 |
| 期待跨版本隐式回退 | 不存在,`(name, version)` 精确解析 |
| 用 lambda 写 upcaster | 泛型被擦除,库在启动期按名字拒绝（这是好事） |

## 12. 本篇不覆盖

- upcaster 误声明在启动期被按名字拒绝——库自己的 `EventUpcasterChainTest` 已覆盖（同名、严格递增、不重复
  来源、类型参数不可擦除）,在 sample 里重做等于测库而不是测流程；
- 两个服务同时启动跑完整链路（与 S4 一样,两侧各自对着 wire contract 测）；
- schema 迁移的机制与不停机步骤——S23,本篇只给出两个顺序里哪个是安全的；
- 死信的重放通道与运维端点——S22；
- 非本体系格式的入站报文与它自己的版本问题——S5。
