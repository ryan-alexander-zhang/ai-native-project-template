# S6 服务间同步调用

对应 sample：`aipersimmon-ddd-samples/s06-synchronous-call-between-services`（两个服务模块）。
场景清单见 [[analysis-00014-ddd-samples-scenario-catalog]]。与
[[analysis-00025-samples-integration-events-across-services]] 的对照是本篇第一节。

## 0. 本篇定位

处理一个请求的过程中必须**当场**拿到另一个服务的结果才能继续。这是其余 sample 都在回避的那种集成：调用在请求
线程里同步发生，调用方的可用性从此**乘上**被调方的。

本篇最重要的一句：**同步调用能拿到"判断"，永远拿不到"预留"。**

## 1. 什么时候该同步，什么时候不该

| | 本篇（风控） | S4（库存） |
| --- | --- | --- |
| 没有答案能不能继续 | 不能——未评估的订单不该存在 | 能——订单先成立，库存随后 |
| 要的是**判断**还是**预留** | 判断，某一时刻有效 | 预留，必须被持有 |
| 对方不可用的代价 | 请求失败 | 没有代价，outbox 等着 |

判据是中间那行，而不是"哪个更快"或"哪个更简单"：

- **判断**（"这单可以吗"）可以同步问。答案在给出的那一刻就开始过期，但判断本来就是这样。
- **预留**（"给我扣住这批库存 / 冻结这笔额度"）同步问不到。对方没有为你持有任何东西，你拿到的只是"刚才可以"。
  真需要持有，就得让对方持有——那是 saga 或分布式事务（S9/S10），不是一次提问。

第一行是必须承认的成本：风控挂了这个服务就下不了单。**这不是待优化的缺陷，这就是"必须拿到答案"的含义。**
工程上唯一的选择是 fail closed 还是 fail open，而那是业务决定——写成"有没有那个 catch 块"，不该是某次吞掉
异常的意外。

## 2. 调用放哪：precheck，不是 handler

库把 `CommandPrecheck` 排在校验（100）与事务拦截器（200）**之间**。调用方的整个形状都由这两个数字决定，
而 sample 直接把它测出来了（在两处读 `isActualTransactionActive()`）：

| | precheck 里 | handler 里 |
| --- | --- | --- |
| 事务是否活跃 | **false** | **true** |

两笔收益：

1. **网络等待期间不占数据库连接。** 同样这次调用写在 handler 第一行就在事务内，一次往返全程占一条连接；一个
   慢依赖于是放大成连接池耗尽——服务死于别处的"慢"而不是"挂"。库的 `CommandPrecheck` javadoc 把这句话写在
   了接口上，本篇只是把它做成了断言。
2. **拒绝的撤销成本为零。** 答案是"不"或"没有答案"时事务还没开始：没有部分写入、没有回滚、没有补偿要写。
   测试同时断言订单表没动、且 handler 从未执行。

**precheck 换不到的东西是原子性。** 它按构造就是 advisory：检查与提交之间世界可以变。所以风控答案是一个
时点判断，不是本服务强制的不变量——这恰好适合风控，也恰好不适合额度冻结（回到 §1）。

## 3. 端口在哪层，适配器在哪层，domain 能不能调

| | 位置 | 理由 |
| --- | --- | --- |
| `RiskAssessments` 端口 | **application** | "另一个上下文怎么看"是用例之间的协作，不是聚合存在的方式 |
| `HttpRiskAssessments` 适配器 | **infrastructure** | 全服务唯一知道有 HTTP 的类 |
| domain | **一点都不碰**（本模块有一条 ArchUnit 规则） | — |

不放 domain 的实际理由不是纯洁性：**会做网络调用的领域模型把不变量绑上了别人的可用性，而且再也不能不带 stub
测试。** 聚合里没有 `riskApproved` 字段，也没有对该服务的任何引用。

端口讲的是**本上下文的语言**：没有 HTTP、没有状态码、没有 problem document、没有对方的 DTO——那些全停在适配器。
返回的是本上下文定义的决定或异常。于是 precheck 能用三行 fake 测，传输换成 gRPC、队列或进程内调用，用例毫无
感觉。

## 4. 对方的 API 契约怎么到调用方

sample 选的是**手写 record**（放在调用方 infrastructure，只带真正用到的三个字段）。三条路各自的代价：

| | 代价 |
| --- | --- |
| 共享 `api` jar | 被调方发版＝调用方重编译；别人要的字段也会到这里；"这个调用方持有哪一版契约"变成 Maven 问题 |
| OpenAPI 代码生成 | 消掉手抄与漂移，代价是 spec 必须已发布、正确、带版本；生成的 DTO 仍然落在你的代码库里，耦合形状不变，只是自动化了。契约大时它是对的 |
| 手写（本篇） | 两个 record；调用方的契约视图恰好是它用到的子集，上游的无关变更在这里是 no-op |

**不是选项的是**：把对方的 DTO 往适配器里面传。

与 S21 的差别值得点明：跨 broker 时"不共享 jar"的理由是**耐久性**（记录活得比代码久，共享 jar 迫使已在途的契约
被协同发版）；同步 HTTP 没有积压，两边同时在线，所以理由变窄了但依然成立——被调方的形状会顺着 jar 长进调用方。

## 5. 两种"不"，不能长得一样

被调方：**拒绝＝200 + `approved: false`**，4xx 只留给"你的请求不对"。两者都有测试。

如果拒绝也用 422，调用方就分不清"业务拒绝"和"我自己的载荷坏了"——一个是给客户看的消息，一个是给工程师的告警。

调用方随后翻译，适配器以上看不到任何状态码：

| 被调方做了什么 | 本服务抛什么 | 客户端看到 |
| --- | --- | --- |
| 200，`approved:false` | `RiskRejectedException`（`ordering.risk-rejected`） | **422**，domain-rule 家族类型 |
| 超时 / 连不上 / 5xx | `RiskUnavailableException`（`ordering.risk-unavailable`） | **503**，自己的 problem 类型 |
| 4xx problem document | `RiskUnavailableException` | **503**——4xx 意味着**本服务**发错了东西，而对自己缺陷的回应不该是告诉客户订单被拒 |
| 200 但 body 读不懂 | `RiskUnavailableException` | **503**——缺失的 `approved` 不等于 `false`，所以客户端 DTO 用装箱 `Boolean` |

最后一条值得停一下：把缺失字段当 `false` 会因为对方改了 schema 而给客户发一片"被拒"；当 `true` 会放过一批未
评估的订单。**都不选：那不是答案。**

### 5.1 库的一个接缝：`ErrorCategory` 没有"依赖不可用"

`RISK_UNAVAILABLE` 只能落在 `UNEXPECTED`，家族默认是 **500**——两处都错：它说故障在本服务，还告诉客户端别重试。
库为此留了两级解析（家族默认 + 按 code 覆盖），所以 sample 用一个 `ProblemCatalog` bean 把这一个 code 覆盖成
**503**。

而 `ordering.risk-rejected` **故意不覆盖**：它和其它业务拒绝共用 domain-rule 家族类型，靠 `code` 区分。这正是
库文档的建议——对外的 problem 类型目录不该随领域错误码一比一膨胀。

## 6. 超时、重试、降级的归属

**超时必须配**：Spring 默认的 request factory 一个都没有。对方接下连接然后不吭声，请求线程就无限期挂着——一个
慢服务于是一根线程一根线程地把调用方拖死。sample 配了 connect 与 read 两个，并写明真实取值是"短于本服务自己的
SLA"。

**重试一次，而且只因为这是 query**：问两遍还是在问。测试**数了请求次数**，所以"重试了一次"是断言而不是愿望——
删掉重试恰好那两条断言变红（负向对照跑过）。改状态的远程调用不能这样重试：没有对方给的幂等键，一次请求会变成
两次额度冻结。

**没实现、只点名**：熔断、隔离舱、跨调用方共享的重试预算。它们属于 resilience 库或 mesh，sample 的诚实做法是
点名而不是半实现一个。

**降级**：fail closed（拿不到答案就不下单）。fail open 对某些产品是合法选择，它应该是 precheck 里一个写明理由的
catch 块——**不能是吞掉异常的副产品**。

## 7. 查询型调用 vs 命令型调用

| | 查询型（本篇） | 命令型（让对方改状态） |
| --- | --- | --- |
| 重试 | 安全，随便重 | 不安全，需要对方的幂等键 |
| 超时的含义 | "不知道答案" | **"不知道对方做了没有"** |
| 放在 precheck | 可以（可重复） | 不可以：precheck 每次 dispatch 都跑，含重投 |

第二列第二行是真正的分水岭：查询超时只是没答案，命令超时是**状态未知**——而未知状态只能靠对方提供的幂等键或
一次对账来收敛。所以本篇的被调方把接口设计成 `Query`，这不是整洁癖，是让调用方的重试与超时有确定语义。

## 8. 没有数据库的服务取哪个 bundle

风控服务只取 `aipersimmon-ddd-starter`，框架的其它一个都不要——persistence / outbox / inbox / flyway 存在的
理由都是"让数据库做点什么"。剩下的仍然值钱：命令与查询总线、拦截器链、id 生成、RFC 9457 problem 响应（一个被
调方需要的正是"能被礼貌地调用"）。

随之而来一个**不可选的属性**：没有 `DataSource` 就没有事务管理器，"一个命令一个事务"的保证无法成立。库不耸肩：
**启动直接失败**，并用 FailureAnalyzer 打印两条出路；真心要这样的部署写 `aipersimmon.ddd.cqrs.transaction.required: false`，
然后**每次启动都 WARN**，免得它变成一个"后来长出了数据库"的服务的无声状态。

`TransactionlessDeclarationTest` 两半都测了：不声明则起不来，声明后能起且上下文里确实没有 `PlatformTransactionManager`。
"我们给无状态服务选对了 bundle"恰好是那种最容易悄悄搞错的判断。

## 9. 这次踩到的三件事

1. **lambda 写的 precheck 在启动期被拒**——prechecks 按类型参数索引，lambda 会擦除它（`Cannot resolve the
   command type of precheck`）。换成带 diamond 的匿名类能过检查，但**它也没运行**；只有写出类型的具名类才可靠地
   带着泛型父类型。与 S21 的 upcaster 注册同一种严格、同一个理由。
2. **`SpringApplicationBuilder.properties(...)` 输给 `application.yaml`**——它贡献的是 *default* properties，优先级
   在配置文件之下。于是启动测试的第一版"证明"了不声明也能起来，实际上是 yaml 里的值赢了。命令行参数才压得住文件。
3. **stub 的默认 executor 是单线程**：一个刻意慢的响应把重试挡在 handler 之外，请求计数器于是声称"没有重试"，而
   重试确实发生了。**stub 的并发度必须匹配客户端可能在途的请求数。**

## 10. 常见错法

| 错法 | 后果 |
| --- | --- |
| 用同步调用去拿"预留" | 拿到的只是"刚才可以"；对方没为你持有任何东西 |
| 远程调用写在 handler 第一行 | 整个往返占着一条数据库连接；一个慢依赖放大成连接池耗尽 |
| 端口定义在 domain | 聚合迟早会调它，不变量从此绑上别人的可用性 |
| 把对方 DTO 往里传 | 对方的形状顺着调用链长进你的模型 |
| 拒绝用 4xx 表达 | 调用方分不清"业务拒绝"与"自己发错了" |
| 把对方的 4xx 当业务拒绝 | 把自己的缺陷说成客户的订单被拒 |
| 缺失的布尔字段当 false | 对方改 schema 变成一片"被拒" |
| 不配超时 | 对方"慢"而不是"挂"时，请求线程被一根根占死 |
| 重试改状态的远程调用 | 一次请求两次冻结（除非有对方的幂等键） |
| 吞掉不可用异常当作 fail open | 降级不是决定，是意外 |
| 依赖不可用报 500 | 既说错了故障归属，又叫客户端别重试；应按 code 覆盖成 503 |
| 无库服务不声明 transactionless | 起不来（好）——但别把它当障碍，它是在阻止一个静默失效 |
| 无库服务照抄 `-starter-mybatis-plus` | 一堆为数据库存在的模块，和一个必然失败的 schema 校验 |

## 11. 本篇不覆盖

- 两个服务互相启动跑完整链路（调用方对着同 JVM 内的真实 HTTP stub 测，被调方对着自己的 API 测）——与 S4/S21
  同一个缺口；
- 熔断、隔离舱、共享重试预算（§6 只点名）；
- 命令型远程调用的落地（§7 只给不对称性；把它做安全需要对方的幂等键，那是 S2 的对面）；
- 跨服务持有预留 —— S9/S10；
- mTLS、调用方身份传播、授权——到目前为止所有 sample 都不覆盖。
