# S12 CQRS 读模型：事件驱动的投影

对应 sample：`aipersimmon-ddd-samples/s12-cqrs-read-model`（两个服务：catalog-service 发布、
ordering-service 持有投影；38 个用例）。场景清单见 [[analysis-00014-ddd-samples-scenario-catalog]]。

## 0. 本篇定位

订单列表页要显示订单 + 状态 + 商品名，而商品名属于另一个上下文、在另一个库里。这一句就是本篇存在的
全部理由。

## 1. 什么时候"直接查写模型"就够了

**S20 是对照，而且是常见情况**：它直接查写表提供列表端点，游标分页做得很正规——对于"本上下文自己数据的
列表"，那就是对的答案，跟行数无关。

逼出投影的只有一列 `display_summary`（商品名）：

| 方案 | 为什么不行 |
| --- | --- |
| SQL join | 不可能。不同库、不同服务 |
| 每行一次同步调用 | 每次渲染列表都把自己绑在对方的可用性和延迟上，一页 N 次 |
| 事件维护的一份副本 | 本篇 |

所以判据不是"查询变慢了"，而是**"查询需要本上下文不拥有的数据"**。自己表上的慢查询是索引问题。
越过所有权边界的形状，或者为了便宜地回答而必须扭曲写模型（同一问题的另一面），才该上投影。

## 2. 三张表、三种生命周期

| 表 | 是什么 | 谁写 | 能删吗 |
| --- | --- | --- | --- |
| `s12_order` / `s12_order_line` | 写模型，真相 | 命令 | 不能 |
| `s12_product_name` | **本上下文对目录名字的副本** | rename 监听器 | 不能，见 §4 |
| `s12_order_list` | 投影 | 只有投影 | 随时能删 |

中间那张最容易被省掉，而省掉它就是投影不可重建的原因。

## 3. 跨上下文的副本算谁的资产（本篇最容易做成后门的一问）

目录拥有商品名。订单服务**持有它显示的那些名字的一份副本**，在自己库里，由发布的事件喂养，并对外提供。
这份副本是订单服务的资产：目录关掉它也能查、能备份、能推理、能重建。

由此三条：

- 订单服务**不可以**读目录的库，它订阅。
- 任何第三个上下文**不可以**读 `s12_product_name`。它不是共享缓存，是一个消费者物化了的订阅。
  没订阅却来读这张表的服务，是找到了一个带 schema 的后门。
- 目录**不可以**知道谁在抄它的名字（有 ArchUnit 规则钉方向）。一个知道消费者是谁的发布方会开始服务他们
  ——一个"给订单列表用的"端点、一份照着别人屏幕形状导出的批量数据——所有权就静默地搬回了它无法被维护的
  地方。

## 4. 同一个值，两个相反的要求（本篇最锋利的一处）

| | 在哪 | 要求 |
| --- | --- | --- |
| `s12_order_line.name_at_purchase` | 写模型 | **永不改变**。发票必须写客户当时同意买的那个 |
| `s12_order_list.display_summary` | 投影 | **跟着目录走**。列表该显示它现在叫什么 |

`thelistShowsTheNewNameAndTheInvoiceStillShowsTheOld` 一个测试断言两边。看见之后就很难再忽略：
**一个被复制的值要么是业务事实、要么是展示缓存，是哪一种决定用什么机制。** 搞反了，就会得到会自己改写的
发票，或者永远不更新的列表页。

## 5. 重建，以及让重建可能的那个输入

`POST /admin/order-list/rebuild` 删掉投影再建一遍，六行。六行只因为两个更早的决定：

1. **整行重算，绝不增量。** `OrderListWriter` 只有一个写方法且接整行，所以事件、改名、重建全都走
   `OrderListProjection.rebuild(orderId)` 并产出逐字节相同的行。按增量维护的投影没有"正确的行"这个定义
   可供比对，它的重建是第二份实现，还得跟第一份保持一致。
2. **副本。** 名字从 `s12_product_name` 读，而不是从消息里直接抄进投影行，所以重建需要的每个输入都是
   本服务自己的表。

`arebuildAfterARenameKeepsTheNewName` 就是为第 2 点付账的测试：**没有副本，重建会产出被冻结的旧名字**，
而唯一的回头路是再问一次目录，或者从 broker 的保留期里重放它的全部事件历史——那是一次带外部依赖和截止
时间的迁移，不是重建。**投影可重建的充要条件是：它需要的每个输入都是你自己的表。**

## 6. 一张表里的两个时钟

| 由什么驱动 | 传输 | 时延 | 怎么断言 |
| --- | --- | --- | --- |
| 订单自己的事实 | 进程内领域事件，在写事务里 | 无 | 直接断言 |
| 商品的名字 | 跨服务集成事件走 Kafka | 可测 | `await()` |

一行列表数据可以同时"对订单是最新的"且"对商品名是落后的"。这不是缺陷，这就是"名字属于另一个上下文"的
含义。把它藏起来只是在替客户猜，所以 `projected_at` 是一列并且返回给调用方。

## 7. 事务阶段买到了什么、没买到什么（这一节被负向对照改写过）

投影用 `@EventListener` 而不是 `@TransactionalEventListener`。我原本写的理由是"同事务才有 read-your-own-
writes"——**负向对照第一次跑出来 0 红，说明这个说法根本没被测到，而且在本应用的形状下是错的**：命令总线
自己开事务、外面没有别的事务包着，所以 `AFTER_COMMIT` 的监听器仍然同步地在 `send` 返回之前跑完，客户
两种写法都能看到自己的订单。买到 read-your-own-writes 的是**投影在进程内**，不是那个注解。

阶段真正决定的是**故障往哪边传**：

| | 在事务里（本篇） | `AFTER_COMMIT` |
| --- | --- | --- |
| 投影抛异常 | 订单下不成 | 订单提交，列表行静默缺失 |
| 投影的 bug 是 | 下单功能的故障 | 看不见的漂移 |

判据因此是：**缺一行比写失败更糟就共享事务；投影昂贵、远程或可选就不要。** 本篇的投影是两条本地语句、
喂的是客户落地的第一个屏幕，所以宁愿拒绝写入。一个要去调 Elasticsearch 的投影答案相反，并且从此需要
本篇不需要的漂移检测。

`apoisonedProjectionTakesTheWriteDownWithIt` 是全服务唯一能区分这两种阶段的测试——它是因为那次 0 红才
被写出来的。

## 8. 一次改名的代价

`RecordProductNameHandler` 返回它重算了多少行，而这个数字就是重点：一次改名 = 一次副本写入 +
**每一个曾经包含该 sku 的订单各重算一行**，无上界，且随商品在售时间增长。

这就是把别人上下文的数据反范式化的账单：查询负载离开读路径，被放大后重新出现在一个你**控制不了频率**的
事件的写路径上。三种收敛办法各是一个独立话题：只重算有人会看的、按版本标记在读时懒重算、或者接受旧名字
到下次重建。"投影一下就好了"不是免费的。

## 9. 负向对照（五个，逐个单跑）

| # | 改动 | 实测 |
| --- | --- | --- |
| 1 | 投影改 `AFTER_COMMIT` | 恰好 1 红。**第一次跑是 0 红**，由此发现 §7 的原说法未被测到且是错的；现在那 1 红的测试是因此才补的 |
| 2 | 改名不再重算已投影的行 | 4 红（其中 2 个是 `await` 超时），量出放大到底买了什么——没有它，列表会一直显示旧名字直到重建 |
| 3 | 去掉未知 sku 的兜底 | 恰好 3 红，最便宜那层（单测）先抓到；summary 里出现 null 而不是占位符 |
| 4 | `renameTo` 永远报告"改了" | 恰好 3 红，同名改名会广播，每个消费者白重算一遍 |
| 5 | 投影去依赖聚合的 `Orders` 端口 | 恰好 1 红（ArchUnit），证明那条规则不是空的 |

## 10. 库的问题：没有新的，确认了一个旧的

没有发现新的库缺陷。确认了一个当时已开的：
[[issue-00161-the-publisher-guard-misreads-a-consumer-as-a-publisher]]——ordering-service 只消费不发布，
但消费方必须把契约标 `@Externalized`（bridge 由此推导订阅的 topic 集），而 Kafka starter 的
durable-transport 守卫看到 `@Externalized` 事件却没有耐久发布者就拒绝启动，于是一个只消费的服务被迫带上
一个它永不使用的 outbox，表一直空着。S12 是**第二次独立撞到**它（S4 是第一次），当时的处置与 S4 相同：
带上并注明原因。

**2026-08-04 已修**：新属性 `aipersimmon.ddd.messaging.kafka.publishes-externalized-events`（默认 `true`），
本 sample 的 ordering-service 因此删掉了 outbox 依赖与 `flyway.components` 里的 `outbox`，改成一行
`publishes-externalized-events: false`。这条 issue 最终在四个 sample 里各留了一处同样的迁就
（S4、S12、S21、S22），四处一起拆掉——**同一条 issue 被独立撞到四次，本身就是"该先修哪个"的答案**。

另外记两条不是缺陷但值得写进文档的交互：

- **两个框架组件 ⇒ 两个 `Clock` bean 且没有 primary**（`outboxClock`、`inboxClock`，都是
  `@ConditionalOnMissingBean(name = ...)` 名字级收口，这是库刻意的设计）。消费方按类型注入 `Clock` 会
  启动失败，报 "expected single matching bean but found 2"。解法是应用自己声明一个名为 `clock` 的 bean 并
  把注入点参数也叫 `clock`（按名字解析）——S7/S9/S11/S20 早就这么做，S12 只是第一次撞上它的必然性。
- **`Projection` 注解的 javadoc 说"in the same transaction"**，那是进程内领域事件驱动的情形；跨服务
  集成事件驱动的投影不可能在同一事务里。同一张投影表两种驱动并存是正常形态（§6），注解的措辞比现实窄。

## 11. 没做的事

| | |
| --- | --- |
| 投影的分页 | S20 的题，且与行从哪来无关。本篇的查询只有一个 limit 和一个排序 |
| 读侧缓存 | S26，清单里就与本篇成对：投影和缓存解决重叠的问题但故障形态不同 |
| 在线重建 | 本篇在一个事务里删了重写，列表会短暂为空。规模上去要写进第二张表再换视图——S23 的地盘 |
| 投影 schema 演进 | 加列意味着重建，而本篇把重建做便宜了；迁移机制归 S23 |
| 投影放独立库 | 现在同一个 datasource，所以投影与写同事务提交。搬走会丢掉这一点并换来独立伸缩——是真实选择，但没有第二个存储就没法诚实演示 |
| 从事件重建 | 本篇的重建读写模型，不读事件日志。从事件重建是另一种架构，带另一种保留期问题 |
