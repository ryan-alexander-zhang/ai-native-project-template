# S25 遗留系统绞杀式接入

对应 sample：`aipersimmon-ddd-samples/s25-strangler-legacy-adoption`（一个部署单元、一个单体 + 一个被切出来的聚合、
48 个用例）。场景清单见 [[analysis-00014-ddd-samples-scenario-catalog]]；本篇是这一系列的最后一个场景。

## 0. 本篇定位

清单说得很准：**库的默认前提是"你拥有 schema"**——版本列、自己铸的主键、租户判别列、框架表。而采用本库的团队
几乎没有绿地项目。所以这一篇的所有前提都反过来：自增主键、没有版本列、几百万行、一个指向未被切出去的表的外键、
以及一套手写 SQL 的 Service。

| 问题 | 答案 | 在哪 |
| --- | --- | --- |
| 怎么选第一个聚合、按什么顺序切 | **写者最少、规则最多**的那张表；两个数都能算出来 | §1 |
| 没有版本列怎么过渡（加列/影子表/悲观锁） | 三个都不重要——**先把第二个写者停掉**，加列才开始有意义 | §2 |
| 自增主键与铸造 id 并存 | 内部保留 `bigint`、**插入前自己取号**、对外从第一天就发 `public_id` | §3 |
| 双写期新旧两路怎么不打架；outbox 能喂新上下文吗 | 能——只对走库事务的写。所以**一个写者、两个读者**，没有"双写" | §4 |
| 遗留代码怎么被 ACL 包住 | 一条 ArchUnit 规则。模式名什么都不买，规则买全部 | §5 |
| 迁移完成的判据、旧路径何时删 | 四个条件，**从代码和 schema 里算出来**，不是开会 | §6 |

**一条库的 issue**：[[issue-00171-the-write-path-against-a-schema-the-library-did-not-design]]（P2，两处
行为都正确但异常信息指向错的原因，而这两处恰好是遗留表必然踩的两处）。

**与清单建议组件的一处偏离，是刻意的**：清单建议用当时的 `-persistence-jdbc` / `-outbox-jdbc`（两者后来都删了，库只留 MyBatis-Plus 后端），理由是"更贴近遗留 SQL"。
本篇的遗留侧**一个框架模块都不用**——纯 `JdbcTemplate` 加手写 SQL，比 JDBC 变体更贴近；新上下文按本系列的既定
约束用 MyBatis-Plus。实测下来有意思的摩擦都在写入路径与 schema 上，与 SQL 方言无关。

## 1. 选哪个聚合先切：两个数，都能算

这一问通常由声音最大的人回答。它有机械答案，而配料已经在单体里了：

- **每张表的写者数**——多少个方法对它发 `INSERT`/`UPDATE`/`DELETE`。这是**成本**：每个写者都是一处要改道或
  留下的调用点，一张有四个写者的表不可能在一次改动里获得单一所有者；
- **每张表的规则数**——挂在它上面的业务逻辑有多少。这是**收益**：一张没有规则的表变成聚合什么都不会得到，
  无论结果看起来多整齐。

实测（`LegacyFanInTest`，从单体源码里数出来）：`legacy_orders` 写者最多，`legacy_refunds` 最少且
**单体表达出来的每一条规则都在退款那条路径上**。所以退款先切。

推广出来的顺序是：**从叶子往里绞**。因为叶子是唯一能在一次改动之后就拥有单一所有者的东西。

判据的两半**各自都不充分**，这一点专门断言了：`legacy_order_items` 写者少但规则为零，切它得到一个什么都不拒绝
的整齐聚合，是没有回报的工作；`legacy_orders` 最终最有价值，**而这正是它不能第一个切的原因**。

这个计算还兼了第二份职：**同一个数后来就是"迁移完成了吗"的判据**（§6）。

## 2. 没有版本列：三个方案都不是答案，顺序才是

清单列了三个过渡方案：加列、影子表、悲观锁。实测下来**在三者之间选哪个不是有意义的问题**——只要第二个写者还在，
三个都保护不了任何东西。

加列本身很容易，也是对的第一步：`NOT NULL DEFAULT 1`（**不是 0**，见 §3.2）让几百万现存行立刻合法、不需要回填。
它**没做到**的是让遗留的 `UPDATE` 对库的检查可见。库的更新语句是 `WHERE version = <loaded>`；一条从不提及该列的
遗留语句把它原地留着，于是谓词命中、遗留的改动被覆盖。

实测（`VersionColumnTest.alegacyUpdateIsInvisibleToTheVersionCheckAndIsSilentlyOverwritten`）：

1. 新上下文读出一条退款，打算拒绝它；
2. 有人用单体自己的界面批准了它——版本列**没动**；
3. 新上下文写入：它校验的版本仍然是当前值，所以没有任何东西拒绝它；
4. 批准消失了，批准人的名字也消失了（被框架的 cleared-column 写入强制成 null），**全程没有异常**。

事后从数据上看不出这是并发缺陷：行是一致的、版本推进了、审计（如果有）记录了一次写入。**这就是"我们加了版本列"
不是"我们怎么让它安全"的答案的原因。**

悲观锁也救不了，而且一句话就能说清：`SELECT ... FOR UPDATE` 只排除**同样去要这把锁**的写者。遗留语句不要，
所以它照走。推广开来：**每一种并发控制都是一份约定，而从未同意过它的写者不受它约束。**

所以真正的答案不是机制而是顺序：**先把第二个写者停掉。** 版本列在遗留路径开始委派的那一刻才有意义，
不是在它被加上的那一刻。实测同一个交错在 `NEW_WRITES` 下变成版本冲突并被拒绝
（`withoneWriterTheSameInterleavingIsRefused`）。

这也是 `s25.refunds.route` 存在的原因，以及为什么它没有 `BOTH` 这一档（§4）。

## 3. 自增主键与铸造 id：拆成两个问题就不难了

"自增主键与 UUIDv7 并存期怎么处理"里其实是两个问题，混在一起才显得难：

1. **聚合的身份是什么？** 过渡期内就是遗留的 `bigint`。外键、遗留代码、以及十年的报表都引用它，而
   **一边换身份一边切聚合是两次迁移套着一顶帽子**；
2. **进契约的身份是什么？** 永远不是那个 `bigint`。一个含义为"某个库里的插入顺序"的数字会泄漏体量、可猜测、
   且无法在两个部署合并后存活。所以 `public_id` 在 V2 就存在，**早于任何一个消费者**。

内部身份由 `RefundId` 包住，所以它上面没有任何东西知道身份是个数据库计数器；对外发的是 UUID，实测 outbox 行的
`subject` 是 UUID 而不是那个数字。两条路创建的行**都**有 `public_id`（新路由聚合铸，旧路由列默认值给），
这正是契约在过渡期内就能安全发布而不必等到过渡之后的原因。

### 3.1 一次预测失败：INSERT 会通过，第二次写才失败

原以为 `saveAggregate` 会拒绝一个没有主键的行——`idValueOf` 的错误信息就是为此写的。**实测不是。** 那个守卫只在
**update** 路径上；insert 路径没有对应检查，于是 `IdType.AUTO` 的行被数据库正常分配了 id。

结果比"被拒绝"更糟：

| | 实测 |
| --- | --- |
| 第一次写 | **成功**，行进库，id 由数据库分配 |
| 内存里的聚合 | id 还是构造时那个，**与行里的不一致** |
| 事件 | 已按那个错的 id 发布 |
| 第二次写 | 才抛 `came back from toRow with no primary key value` |

也就是错误归属**已经落库、已经流到下游**，才有人报错。所以对遗留 `BIGSERIAL` 表的规则不是"库会拦住你"，
而是"自己取号，因为没有东西会拦你"。取号用表自己的序列（`nextval(pg_get_serial_sequence(...))`），
这样两条路的编号同源、不可能撞——实测三次交替插入 id 严格递增且互不相同。

### 3.2 版本列默认值必须是 1，这一个字符值一段话

库用 `version == 0` 表示"尚未持久化"并走 INSERT。遗留表加列时最自然的写法 `DEFAULT 0` 会把**每一行历史数据**
都设成那个"未保存"的值，于是**对任何迁移前旧行的第一次写入都是 INSERT 一个已存在的行**。

实测（负向对照 1，把 `DEFAULT 1` 改回 0）：**2 红 / 48**，关键那条抛 `DuplicateEntityException`，而它列出的两个
可能原因在这里**都不成立**——没有并发创建，工厂也没忘 `restoreVersion`（它老实还原了列里的 0）。

两处都开进了 [[issue-00171-the-write-path-against-a-schema-the-library-did-not-design]]：行为都对，信息都指错方向，
而这恰好是遗留表必然踩的两处。

### 3.3 顺带一处：ORM 不认识的列类型

`public_id` 是 PostgreSQL 的 `uuid`，而 MyBatis 只为规范点名的 JDBC 类型出厂了 type handler。报错是
`Type handler was null on parameter mapping for property 'publicId'`，读起来像映射写错了，实际是 ORM 从没听说过这个
列类型。三条出路：把属性映成 `String`（要连接级 `stringtype=unspecified`，为一个小问题动一根大杠杆）、
把列改成 `VARCHAR(36)`（为迁就 ORM 去改遗留表）、或者写十五行 handler。本篇写了 handler，因为它局部、显式，
且如果那一列哪天没了它也就没了。

这是本篇大多数迁就的形状：**schema 不会为框架改，所以适配器吸收差异，并且在一个地方说明。**
（`autoResultMap = true` 也要一起加，否则 handler 只在写的方向生效、读回来是 null，这是同一个问题里更迷惑的一半。）

## 4. 双写：不要。一个写者、两个读者

清单问"双写期间新旧两条路如何不打架，outbox 能不能用来把事实喂给新上下文"。两个答案，第二个让第一个变得无关：

1. **能，outbox 是有效的**——对走库事务的写。行与聚合同一次提交落地，这是 S8 的保证，在一张库没设计过的表上同样成立
   （实测新路径写入后 outbox 恰好 1 行）；
2. **而遗留路径根本用不了它。** 没有 `IntegrationEvents`、不参与库的事务、也没有东西去写那行。实测遗留路径插入后
   **outbox 为 0**——不是配置漏了，是 outbox 行由发布方的代码写，而单体不发布。

于是三条退款、两条路径，表里 3 行、feed 里 2 条。比"有延迟"更糟的是**这个差不是延迟**：等下去不会好，因为没有东西
在路上。建立在 feed 上的消费者无法区分"还没发布"与"永远不会发布"，这个性质让双写之上的对账器无法收敛——除非它直接
去读表，而那时 feed 就是装饰。

**所以 `LegacyRefundEntryPoint` 没有 `BOTH` 这一档。** 迁移期人人都会伸手去拿的那个安排（两边都写、事后对账）在这里
没有机制支撑。

还有一条属于遗留 schema 而不属于库的：**连轮询对账都没有可靠水位线**。单体的 `updated_at` 是每条 `UPDATE` 手写维护的，
而 `addNote` 忘了写——实测行变了、时间戳没变。修它的地方不在新上下文里。

## 5. ACL：两个类，和一条规则

清单问遗留代码如何被 ACL 包住而不是被到处直接调用。有用的答案不是模式名，**是一个数字**：整个服务里只有一个类可以碰
`legacy` 包，而这件事由一条 ArchUnit 规则说着（`onlyTheAclTouchesTheLegacy`）。ACL 的其余性质都从这条约束推出来；
把它叫做 ACL 什么都推不出来。

实测（负向对照 2）：给一个 handler 加上 `LegacyOrderService` 依赖——就是那句"先这样，它只要一个字段"——
**1 红 / 48，2 处违规**。没有这条规则，第一件发生的事就是这个，第二件不会被评审。

ACL 里发生三处翻译，每一处都是一个遗留事实止步于门口：一个有四个取值、不太算枚举的状态字符串变成聚合真正推理的那个
布尔；`EmptyResultDataAccessException`——Spring JDBC 的异常，因为单体用 `queryForObject`——变成 `Optional.empty()`；
`LegacyOrderRecord` 不出现在返回类型里。

实测（负向对照 3）：去掉异常翻译，**1 红 / 48，而所有 ArchUnit 规则全绿**——一个漏出去的异常类型不是依赖违规。
这是两类检查的分工：规则管"谁能看见谁"，测试管"看见之后翻译了没有"。

两个设计决定值得点出来：

- **端口声明在新上下文的 application 里，不在 ACL 里。** 新上下文说出它需要什么，ACL 负责从单体现有的东西里满足它。
  反过来声明的话，遗留词汇就决定了接口形状——而一个发布遗留形状的 ACL 不是 ACL，是转发地址；
- **委派入口点住在 `acl` 而不是 `legacy` 里。** 它依赖新上下文，而 `legacy` 上那条规则是单体不许依赖新代码
  （`thelegacyDoesNotGrowNewRoots`）。装在单体里的委派 shim 会是新代码往旧代码里长回去的第一根线，第二根不会被评审。

第三条规则比库的隔离规则更严，理由与封装无关：**能读单体的聚合，是不变量依赖遗留 SQL 的聚合**
（`thenewDomainCannotSeeTheLegacy`）。订单的事实作为参数到达 `Refund.raise`，这正是 `RefundTest` 不需要数据库、
毫秒级跑完的原因——而"模型需要一个 stub 才能测"是边界不再是边界的征兆。

## 6. 完成的判据：四个条件，算出来的

四个条件，每一个从代码或 schema 里读：

1. **没有遗留方法写那张表。** 选第一个聚合的那个计算（§1）数写者，判据是这个数归零；
2. **没有东西到得了遗留方法。** 路由是 `NEW_ONLY` 且方法体已删除；
3. **指向未切出表的外键消失了。** 在此之前那张表不能搬去另一个数据库，所以"已切出"只在一个部署内成立；
4. **聚合不拥有的那些列有了归属。** `created_at`/`updated_at` 还是单体的，而有一个遗留方法不维护它们——
   于是相信它们的读者是在相信没人拥有的东西。

**本篇刻意没有完成**，而 `DoneCriterionTest` 用数字说出这件事：退款表仍有遗留写者、外键仍在、两个无主列仍在。
只展示完成态的 sample 会跳过要花十八个月的那部分。

判据关于**代码**而不是关于配置，这是刻意的：配置值可以被没读过这些文件的人改掉。

已经为真且可测的三件（免得判据只是一张欠债清单）：每一行都有对外身份（无论哪条路创建），规则集中在一处并且会拒绝，
版本列正在被参与的那个写者推进。**这就是一次抽取买到的东西**——上面那张清单是它没买到的。

那么什么时候把旧路径删掉？条件 1 到 4 全绿的时候。而在那之前，把遗留方法体**留着**是刻意的：留着让切换可以由一个
配置值回退，而不是靠回滚——这是"一个糟糕的下午"和"一个糟糕的星期"之间的差别。

## 7. 唯一一处刻意的行为变更

抽取应当保持行为不变，本篇有一处例外并且把它写下来：遗留的 `approveRefund` 返回 `void` 并把"已经批准过"咽掉，
新的会拒绝。依赖那份沉默的调用方现在会看到 409。

`ApproveRefund` 的 javadoc 里点明了，`StranglerTest.asecondApprovalUsedToBeSilentAndIsNowARefusal` 把**新旧两种行为
并排断言**——因为**没被写下来的行为变更，六个月后和一次回归无法区分**。

同类的还有一条更需要小心的：`ALREADY_OPEN` 是单体**完全没有**的规则。引入它是有意思的那种风险——旧路径允许它，
所以生产库里可能已经有违反它的行。这是"上线规则前先查数据"的理由，不是"跳过规则"的理由；也是本篇 V2 迁移**故意
没有**加部分唯一索引的原因：**一个会拒绝现存行的约束，失败的是部署而不是请求。**

## 8. 负向对照（逐个单跑，逐个量）

一次只改一处，跑完量红数，从 scratchpad 备份还原（不用 `git checkout --`），还原后逐个 `diff -q` 核对。

| 改动 | 实测 | 值得注意的是 |
| --- | --- | --- |
| 版本列 `DEFAULT 1` 改回 `DEFAULT 0` | **2 红 / 48** | 关键那条是**对任何旧行的第一次写入**抛 `DuplicateEntityException`，而它给出的两个原因都不对（issue-00171） |
| 一个 handler 直接依赖 `LegacyOrderService` | **1 红 / 48**，2 处违规 | 就是那句"先这样，它只要一个字段"。没有这条规则它不会被评审 |
| ACL 不再翻译 `EmptyResultDataAccessException` | **1 红 / 48** | **所有 ArchUnit 规则全绿**——漏出去的异常类型不是依赖违规 |
| 路由改回 `LEGACY_ONLY` | **12 红 / 48** | 每一条规则、每一次拒绝、以及发布出去的那个事实，全部消失。这是整次抽取的价值写成一个数 |

最后一个对照顺带说明了一件事：`alegacyUpdateIsInvisibleToTheVersionCheck` 在 `LEGACY_ONLY` 下**照样绿**——
因为那条发现关于"两个写者"，而 `LEGACY_ONLY` 下仍然有两个。它不依赖路由，正如它不依赖版本列。

## 9. 没做的事

| | |
| --- | --- |
| 切第二个聚合 | §1 的顺序说了 orders 最后切。真正做它需要把四个写者逐个改道，而那是同一套动作重复四遍 |
| CDC / Debezium | §4 的结论是"一个写者"，所以不需要它。需要它的场景是遗留侧无法改道，那是另一篇 |
| 影子表方案 | §2 的结论是三个方案都不解决问题，所以只把最便宜的那个（加列）做到位并量了它的边界。影子表还额外带来两个真相源 |
| 真正删掉旧路径 | §6 的判据未满足，而伪造一个满足的终局会跳过这一篇最该展示的部分 |
| 几百万行的性能 | 加列用 `DEFAULT` 在 PG 11+ 不重写表，这是本篇唯一涉及体量的决定；索引与批量回填的度量是 S23 的题目 |
| 遗留侧的租户列 | 本篇的单体没有多租户，加一列会把两个正交的迁移搅在一起（S13 讲传播） |
| 外键真的拿掉 | `DoneCriterionTest` 把它算成未完成条件之一，拿掉它属于"切 orders"那一步 |
