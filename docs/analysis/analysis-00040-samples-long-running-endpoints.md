# S28 长耗时与大数据量端点

对应 sample：`aipersimmon-ddd-samples/s28-long-running-endpoints`（一个部署单元、77 个用例）。
场景清单见 [[analysis-00014-ddd-samples-scenario-catalog]]；同步接口的既有讨论见
[[analysis-00024-samples-scheduled-and-batch-entries]]（S11 划下的边界，本篇接着它往下走）。

## 0. 本篇定位

一个导出与一个导入，都做不完在一次请求里。清单问了六件事，本篇把每一件都做成可测量的数字而不是形容词：

| 问题 | 答案在哪 | 量到了什么 |
| --- | --- | --- |
| 同步接口的上限在哪 | `SynchronousLimitTest` | **不在任何超时上，在连接池上**；库不设任何时间上限 |
| `202 + 作业资源 + 进度查询` 契约怎么定 | `ExportController`、`JobContractTest` | 客户端给 id → 不需要幂等键存储 |
| 作业状态该不该是聚合 | `ExportJob`、`ProgressIsNotAnInvariantTest` | **生命周期该，进度不该**；一次进度 tick 足以拒掉一次取消 |
| 为什么不该用 process-manager 当作业队列，正面替代是什么 | `NotAJobQueueTest` | 20 次进度 = 21 行 transition + 21 个 revision；1 MiB 载荷上限 |
| 大导出怎么流式而不撑爆内存 | `StreamingExportTest` | 游标要**同时**满足事务与 fetchSize，缺一个静默失效 |
| 上传的分片、断点、幂等 | `ChunkedUploadTest` | 20 个分片，批次聚合一次都没被重写 |

**本篇没有发现库的功能缺陷。** 唯一开的 issue 是一条文档缺口
（[[issue-00169-nothing-warns-that-a-hand-written-write-must-advance-the-version]]，P2），
而它恰好是本篇最锋利的那个负向对照量出来的。

## 1. 同步接口的上限：不在你以为的地方

问"一个同步接口最多能跑多久"，通常得到的答案是某个超时：负载均衡器的 60 秒、客户端的读超时、
网关的。这些都真实存在，而且都是**最后**才咬到的。

先咬到的是连接池，它的算式没有任何余地：**并发 × 时长，对上池子大小**，而整个服务的其他部分——
包括健康检查——排在后面。

实测（`SynchronousLimitTest`，池子调成 2、获取超时 1 秒）：

- 两个并发的流式导出各持一条连接 → 一个**与导出毫无关系**的 `SELECT 1` 拿不到连接而失败；
- 失败的形状值得注意：**不是慢接口超时，是无关接口拿不到连接**。所以从症状找不到原因——坏掉的
  端点永远不是有问题的那个；
- 慢活一放手，池子自己就好了，不用重启。

两个池子大小与两个并发是同一个算式，十对十、五十对五十也是。那个四分钟的端点不需要很受欢迎才能把
服务弄停，它只需要和池子一样宽。

**另外量了一条"别指望框架"**：库对 command / query / handler **不设任何时间上限**，一个 handler
要跑多久就跑多久（`thelibraryImposesNoTimeLimitOfItsOwn`）。"总会有东西把它掐掉吧"是让四分钟端点
进生产的那个假设。

还有两件同步接口在**任何**规模下都做不到的事，写在 `InlineExport` 的 javadoc 里：报告进度
（没有地方可报——调用方正阻塞在响应上），以及安全重试（三分钟超时的客户端无从知道活干了没有，
于是重试，于是两个导出在跑）。

顺带说清楚一件常被混淆的事：`InlineExport` **是流式的**，它一次只持一行。流式修好了内存问题，
把事务时长问题原封不动留在原地，而后者才是把服务弄停的那个。

## 2. 游标：两个条件，缺一个都不报错

这是本篇最机械也最容易中招的一条。一个"看起来在流式"的读要真的流式，三件事必须同时成立，而
**其中两件不在 mapper 文件里**：

1. `ResultHandler` 而不是 `List` 返回 —— 在 mapper 上。少了它 MyBatis 无论驱动怎么做都会建整个列表；
2. `fetchSize` —— 在 mapper 的 `@Options` 上。PostgreSQL 驱动只在被告知一次取多少时才开服务端游标；
3. **一个事务** —— 在**调用点**。同一个驱动在 autocommit 下会完全忽略 `fetchSize`，把每一行读完再
   把第一行交给你。

三者缺任何一个，**什么都不会失败**：查询照样返回全部行，代码每一层看起来都像流式，内存没了。

怎么确定性地量出来（`acursorNeedsBothATransactionAndAFetchSize`）：用一条**最后一行必然报错**的查询
（`1 / (CASE WHEN id = <max> THEN 0 ELSE 1 END)`，且不带 `ORDER BY`，让 PG 逐行产出）。服务端真在流式，
客户端在错误到达前已经看到前面的行；驱动缓冲了，则一行都没看到。不看时间、不看堆、不会 flaky。

| 条件 | 错误前收到的行数（共 5000 行） |
| --- | --- |
| 事务 + `fetchSize=500` | **4500** |
| autocommit + `fetchSize=500` | **0** —— fetchSize 被静默忽略 |
| 事务 + `fetchSize=0` | **0** —— 没有游标 |

4500 而不是 4999 本身就是证据：驱动整批交付，装着出错那行的第十批从未到达，所以这个数是 fetchSize
的整倍数——**一个整数同时证明了"在流式"和"批大小被采纳"**。

用原始 JDBC 而不是 mapper，因为被量的两个条件是连接与语句的属性，套一层 MyBatis 只会加一层不可能
改变答案的东西。

**这就是为什么 sample 自己的读会拒绝在没有事务时运行**（`MyBatisExportSource`）。一个从结果里检测不出
缺失的前提，必须在干活之前检查，否则等于没检查——库在 `saveAggregate` 里做的是同一个动作。

一个诚实的缺口，第 9 节的对照 5 量出来的：把 `fetchSize` 从 mapper 上删掉，**77 个用例里只红 1 个,
而那一个是断言注解本身的**。行为层面全绿——5000 行的流式测试在整个结果集被缓冲的情况下照样通过。
所以那条注解守卫比周围的测试弱，是故意的：它断言的是配置而不是行为，因为这个回归**没有行为症状**。

## 3. 一次快照还是分页扫过去：两个都对，不是同一份文件

`SNAPSHOT`（一个只读事务、一个服务端游标）与 `CHUNKED`（keyset 分页、每页自己的短事务）都正当，
而且**不等价**。实测（`asnapshotReadAndAChunkedReadDisagreeAboutRowsThatArriveMidExport`）：导出开始后
从另一条连接插一行，

- SNAPSHOT：1200 行 —— 一个事务，一幅图；
- CHUNKED：1201 行 —— 那行排在游标之后，被后面某一页捡到了。

代价也是对称的：SNAPSHOT 的事务开着整场导出，PostgreSQL 上这会压住 xmin horizon，autovacuum 在这段时间
里回收不了更新的东西——四小时导出就是 vacuum 计划上的四小时空洞，这是 DBA 会来问的那件事。CHUNKED 没有
长事务、worker 死掉只丢一页，代价是文件成了若干时刻的并集而不是一个快照。

**错的不是选哪个，是不知道自己发的是哪个。** 所以两种都在 main 里，由 `s28.export.read-mode` 选，
差异被量出来而不是被断言。

分页用 keyset 不用 `OFFSET`：offset 让数据库走过并丢弃页前的一切，第 2000 页的成本是第 1 页的两千倍，
整场导出对页数变成二次的。读侧契约沿用 S20。

## 4. 作业状态该不该是一个聚合：生命周期该，进度不该

**生命周期该。** `ExportJob` 上的每一条都是有人会被拒绝的事：不能成功两次、不能没有产物就成功、
不能被一个认领已被接管的 worker 结束、请求在提交时就定死了不能在运行中被改。一张带 status 列的表
拒绝不了任何一条。

**进度不该，而理由是机械的而不是审美的。** 进度什么都决定不了：没有规则读它，没有拒绝依赖它，丢一次
tick 谁都不损失——而它一场跑要变几千次。实测（`ProgressIsNotAnInvariantTest`）：

- 1000 次 tick，**聚合的 version 一动不动**，进度表就 1 行，原地覆盖;
- 反过来会怎样：**一次**顶替"经过聚合的进度 tick"的 version 自增，就足以让一次已在途的取消
  `OptimisticLockingFailureException`。一个一场跑变几千次的计数器，和用户正在等的那个决定共用一个
  version，结果就是决定输——反复输，而且从外面没人解释得清为什么;
- 进度放对了地方，同样的交错就是非事件：1000 次 tick 之后取消照样落地。

所以这条判据可以推广：**一个数据要不要进聚合，问的是"有没有规则读它"，不是"它属于谁"。** 进度、
分片收据、审计正文都属于这个作业，都不进它的一致性边界。

### 4.1 进度的事务比进度的表更要紧

写在聚合外面还不够。一次写在导出自己事务里的 tick，对**所有其他人**在那个事务提交前都是不可见的——
而对长导出来说那正是进度不再有趣的时刻。

默认实现让每次 tick 在自己的连接上立刻提交（`REQUIRES_NEW`）。实测：在读事务还开着的时候，
**从第二条连接**能读到 4100 这个值（`atickIsVisibleFromAnotherConnectionBeforeTheReaderFinishes`）。
用第二条连接是必须的——用同一个事务读回来什么都证明不了，因为事务永远看得见自己未提交的写入，而这正是
`SAME_TRANSACTION` 那个错误能通过它自己作者的测试的原因。

反例照样发货并被量过（`ProgressInTheSameTransactionTest`，专门一个上下文）：写者自己看得见 4100，
别人读到"没有这一行"，提交之后才突然出现。客户端轮询、看不到东西、判定作业卡住了。

代价也说清楚：**一个在跑的导出因此持两条池连接而不是一条**。还有一个反向的好处——进度能活过导出的
回滚，这是对的，行确实读过了，而失败作业最后到过哪里正是查问题的人要的。

顺带撞出一条一般性的事实，它比这个 sample 大：**一个长读一旦开始报告自己，它就不再是只读的了**——
除非报告走别处。只读事务在 PostgreSQL 上拒绝其连接上的一切写入，所以 `SAME_TRANSACTION` 模式与那个
本该打上的 `readOnly` 标记无法共存，`ExportRunner` 在选了该模式时把标记摘掉。

## 5. 认领必须是手写 SQL，代价是必须自己动 version

这是全篇唯一一处**故意不走聚合**的写入，理由在 `ExportClaims` 的 javadoc 里：

乐观锁是为"本不该有人进入的竞争"造的——两个写者碰了同一个聚合，一个被拒，而这个拒绝是信息。
认领恰好相反：N 个 worker **本来就该**抢下一个作业，N-1 个抢输不是新闻。写成读-改-存不只是吵，是错：
每个 worker 都读到同一个最老的排队作业，一个赢，其余得循环重读，于是十个 worker 的机群九成的轮询都
撞在同一行上。

所以认领是 SQL：`FOR UPDATE SKIP LOCKED` 选候选 + 一条重新校验条件的 `UPDATE`。这是库给自己的 outbox
中继与 process-effect 中继写的形状，连三个列（owner、到期、条件更新）都一样，sample 照抄而不发明变体。
S11 已经点出过这条边界并把这一侧留着：**没有版本可仲裁的活，得先认领再干**。

**代价，以及付账的方式。** 手写 SQL 与版本化写入要在同一张表上共存，只有一个前提：那条 SQL 必须
自己 `version = version + 1`。不然一次在认领之前读到作业的取消照样提交——它校验的版本确实还是当前值——
于是作业变成 CANCELLED 而某个 worker 正把它跑完。

对照 1 量的就是这个：去掉那个自增，**只红 1 个，而红的方式是"没有抛异常"**。事后从数据看不出这是并发
缺陷，它看起来就是一次成功的取消。这条前提库里一处都没写过，见
[[issue-00169-nothing-warns-that-a-hand-written-write-must-advance-the-version]]（P2，三句话的文档修法）。

### 5.1 两个竞争，两个不同的守卫

长耗时的活是**被认领**而不是被派发的，于是有两件同步 handler 从不会遇到的事，而它们需要不同的答案：

| | 是什么 | 守卫 | 为什么不是另一个 |
| --- | --- | --- | --- |
| 停住的 worker 活过来 | 租约过期、别人接管、它要来报告一个已被取代的结果 | `ExportJob.requireHeldBy`，显式检查 owner，抛 `LEASE_LOST` | **不能交给乐观锁**：版本冲突会被重试拦截器重试，而这里重试会重读作业并覆盖新主人的成果。栅栏必须拒绝，不能重试 |
| 请求撞上认领 | 取消在认领前读到作业 | 乐观锁——而且只因为认领动了 version | 显式检查在这里没用：取消看到的状态本身就是旧的 |

心跳还有一个反直觉的约束：它**不能**动 version。worker 手里正握着一个打算在导出结束时写回的聚合，
一个自增版本的心跳会把 worker 栅在它自己外面——作业每个租约周期被唯一还在干活的进程放弃一次，永远。

对照 2 量的是第一个守卫：去掉 owner 检查，**4 红 / 77**，两个在单元层两个在集成层，其中
`astalledWorkerCannotReportAnOutcomeAfterTheTakeover` 直接显示被取代的那次运行被落盘了。

### 5.2 一个副产品：产物的写入按名字幂等

被取代的 worker 在被拒绝之前**已经把文件发布了**（草稿先 commit，再报告结果）。这不是漏洞：两个 worker
写的是同一份内容、同一个最终名字，`ATOMIC_MOVE` 覆盖过去而已。at-least-once 的活能这样安排，正是因为
产物的写入按名字幂等——如果产物名里带了 attempt 号或时间戳，这一条就不成立了。

## 6. 取消是一个请求，不是一个状态

排队中的作业取消是即时的（什么都没跑、什么都没写）。**在跑的**作业只记一个标记，worker 在下一个分片
边界确认并调用 `cancelled`。外面没有任何东西能把一个在跑的作业直接置为 CANCELLED，这正是重点：
从外面强加的取消会产出**产物在磁盘上而状态是 CANCELLED 的作业**，而读状态的人永远不会想到去找那个文件。

推论是 `succeeded` 在取消已被请求之后**仍然允许**，sample 宁愿把这句写出来也不藏着：活干完了、文件写好了，
在最后一行刷盘时到的请求取消不掉它。在这里拒绝这次成功，会留下一个带产物的 CANCELLED 作业，严格地更坏。
客户端靠轮询知道自己晚了一步——它本来就要轮询。

也因此没有第六个状态 `CANCELLING`：客户端从它身上学不到"RUNNING + 我刚发的取消"之外的任何东西，
而 worker 根本不看它。请求就住在作业上的一个标记里，因为它就是一个标记。

发现取消的粒度 = 发布进度的粒度 = `progress-interval` 行。不更密，因为取消没有紧急到值得每行一次查询；
不更疏，因为这个间隔同时是"取消之后多久活真的停下"，而那是会被问到的数字。

## 7. 为什么不该用 process-manager 当作业队列，以及正面替代

S9 给过"什么时候不该再用 process-manager"的判据（需要人参与的等待、需要动态拓扑、需要跨语言可视化编排）。
清单这一条问的是另一件事：为什么**这个**——一个带进度、带取消、带输出产物的长耗时计算单元——不能建模成
一个流程，以及正面的形态是什么。S9 只问了上限，没给替代。

四个答案，每个都是对着**真引擎**量的（`NotAJobQueueTest`，流程定义在 test scope，因为 sample 不该发货
它正在警告的形状）：

1. **载荷上限 1 MiB**（`payload.max-bytes` 默认值），一个月的对账行不是 1 MiB。实测抛
   `ProcessPayloadTooLargeException` 并报出 `1048576`。所以产物只能是引用——这本身就是对的，也正是要点：
   一旦 state 变成一个指向流程管理器既没写过也清理不了的文件的指针，那个持久流程就是在给一件它不参与的活
   做账。本篇的聚合拿着同一个指针，机械成本是它的十分之一。
2. **每一次进度 tick 都是一行持久 transition 加一次 revision 自增。** 实测 20 次 → **21 行 transition、
   revision = 21**。对照就是断言：同样 20 次报告在本篇的设计里留下 1 行、原地覆盖、**完全不碰作业**。
   乘上真实导出的 tick 次数，transition 表会变成库里最大的东西，装着一个计数器的历史。保留期也救不了：
   库的 cleanup 默认关，且是"完成后留三十天"，那是给会结束的流程的策略，不是给消防栓的。
3. **进度与取消是同一条 revision 校验车道，于是互相串行。** 实测：20 次 tick 之后到的取消是
   **revision 22，不是 revision 2**。那 20 次每一次都是取消必须排在后面的写入；真并发下每一次都是取消被
   拒绝并重试的机会，而库的重试上限是 3。
4. **除了喂给它一个输入，没有别的办法让实例停下。** 对着**库自己的 API 面**断言：`ProcessRuntime` 只有
   `start` 和 `handle`，`ProcessQuery` 只有 `find` 和 `findRef`。这对协调器是对的（没有后门改状态），
   对作业是问题——运维的"停"不该被流程当时所在的那个步骤当作 `ignored` 吸收掉，而唯一可用的杠杆恰好是
   一个定义有权忽略的输入。

还有一条不需要测量的：`ProcessDefinition` 不做 I/O（库的 javadoc 明确列了：no repository、HTTP、
command bus、时钟、随机、Spring bean、第三方 SDK）。所以真正的导出**不可能**在定义里，它只能在一个
`DispatchCommand` 效应的 handler 里——也就是活发生在流程管理不到的地方，流程只记下了"开始了"。

**正面替代**，就是这个 sample 的其余部分，而且一点都不新：

- **认领 + 租约**（第 5 节），形状照库自己的中继；
- **生命周期进聚合**，因为每一次转移都是规则（第 4 节）；
- **计数器留在聚合外**，因为它什么都不决定（第 4 节）；
- **产物按引用存**，因为事务里的东西必须小（第 2、5.2 节）；
- **`202` + 一个可轮询的作业资源**（第 8 节）。

这些都不是对 process-manager 的反对。**流程管理器协调别人的活并记住有什么要撤销**，每一步的活发生在
别处、耗时毫秒；**作业本身就是那件活**。两者对存储的要求正好相反。

ArchUnit 里有一条规则钉着这个立场：main 代码不许依赖 `com.aipersimmon.ddd.processmanager..`。写成规则
而不是注释，因为下一次某个流程需要一步时，那个依赖正是有人会去拿的。

## 8. `202 + 作业资源 + 进度查询` 的契约

五个端点，`ExportController` 里逐条给了理由，这里只留最有争议的三条决定。

**`PUT` 加客户端提供的 id，不是 `POST`。** 这一个选择让提交天然幂等，不需要幂等键存储：第二个相同的
请求指名的就是那个已经存在的作业。S2 需要键存储，因为它创建的资源 id 由服务端分配，请求里没有任何东西
能标识第一次尝试。

这还顺手绕开一个容易踩进去的错配：一份存下来的幂等结果有保留窗口（通常几小时），而一个作业有生命周期
（月末导出可能是几天）。一旦窗口是两者里更短的那个，**客户端重试一个已被接受但没做完的请求会拿到第二个
作业**，本该防重的契约生产了一个重复。客户端提供的 id 没有窗口——资源就是那份记录。

同一个 id 换一个 period 则是**拒绝**（`REQUEST_MISMATCH`）：这就是幂等键存储的 `Mismatch` 结论，
由资源自己表达出来。

**两次都是 202，两次都带 `Location`。** 超时后重试的客户端不能分辨自己的重试和自己的第一次尝试，
否则它会在这个差别上分支——而它无从知道两次里哪一次到了。这次调用是否创建了作业写在 body 里，给人看。

**202 上不放 `Retry-After`。** 它会是在最糟糕的时刻（任何活都还没发生）做的一次猜测。诚实的节奏提示是
客户端马上要轮询的那个进度读数：十秒后到了 4% 比任何提交时刻写下的 header 都说得更多。

作业资源上五个字段各自的存在理由写在 `ExportJobView` 的 javadoc 里，判据统一是"少了它会把人送去问活人"：
status（做完了吗）、progress（卡住了吗——status 答不了）、attempt（是不是一直在出错）、failure（为什么）、
contentPath（字节在哪，而且只在真有字节时才出现）。progress 里带 `updatedAt`，因为那是**唯一**能让客户端
把"慢"和"卡住"分开的字段，而这个区分正是进度查询存在的全部理由。

下载读文件，不读表（`ExportDownloads`、`ArtifactStore`）。把查询结果直接流进 HTTP 响应，等于让客户端的
网速决定一个数据库事务开多久：慢链路上的调用方、或者读一半就不读了的调用方，想持多久就持多久。一旦导出
是个文件，下载就是一次文件读——可取消、可续传、和数据库完全无关。

早问的下载是 **409 而不是 404**（`ARTIFACT_NOT_READY`）：作业存在、调用方 id 也对，回答"没这东西"会
把人送去检查 id 而不是去等。这与 S27 对被隐藏行画的是同一条线。

## 9. 上传：分片、断点、幂等

一个可续传的上传只有一个想法：**每个请求都能重放**。断点续传按定义就是一个不知道自己发出去的东西有多少
到了的客户端——那正是故障销毁掉的信息。所以服务端必须回答"你还要什么"，而每个动作必须容忍被重放。
两者都不是优化：少了它们，掉线之后唯一的恢复方式是整份重发，而对当初让上传分片的那种体积来说，那不叫恢复。

实测的几条：分片可以乱序、可以并行、可以重发（第二次是 no-op 而不是错误）；`GET` 返回**还缺哪几个编号**；
完成在任何分片缺失时被拒绝并**点名缺哪几个**；完成本身幂等且行数只算一次；校验和不对的分片被拒绝且不留
记录；超出声明范围的分片被拒绝；完成之后到的分片被拒绝；放弃是带原因的另一种关闭方式——少了它，一个被
放弃的批次和一个客户端马上要回来的批次无法区分，于是什么都清理不了、id 永远被占着。

分片编号在 URL 里而不是从到达顺序推出来，这才让"哪些落了"是一个有确切答案的问题而不是一个水位线。
校验和与主键给的是**两种不同的保证**：主键说"我们已经有第 7 片了"，校验和说"而且它是你想要的那个第 7 片"。
掉线最常见的失败是截断，而截断只有校验和抓得住。

**分片收据不属于批次聚合**，理由与进度同构：一千片的上传会给批次一个一千元素的子集合，每次保存全量重写，
而这些值彼此之间不承载任何不变量——第 7 片到了，关于第 8 片什么都没说。所以收据在自己的表里，由自己的
mapper 写，而批次在有人要求完成时**被告知计数**（`ChunkTally`）。这与 S27 的擦除闸口是同一个安排：聚合把
计数当参数收下。安全性来自决定仍然发生在一次版本化写入里——两个并发的完成读到同一个 tally，都调用
`complete`，其中一个在 version 上输掉。

实测：20 个分片之后，**批次聚合的 version 与刚打开时一样**（`twentyChunksLeaveTheBatchAggregateUntouched`）。

有一个缺口是点名的而不是藏起来的（`AcceptChunkHandler` 的 javadoc）：批次可能在"检查开着"和"插入收据"之间
被完成，于是一片能落在刚关闭的批次上。保护来自完成本身——它在版本化写入里自己核验 tally，所以迟到的一片
不能让一个已完成的批次变错，只能留下一条孤立的收据。这也是为什么已完成批次的行数取自它核验过的那个
tally，而不是事后再数一次表。

分片载荷是 JSON 里的一个字符串，这是 sample 故意做的简化：multipart 与 content-range 是 HTTP 细节，而本篇
关心的问题——什么是幂等的、什么被校验、"可续传"要求服务端记住什么——两种传法下完全一样。

## 10. 失败的可见性与重试

失败的作业带着原因留在作业资源上，不只留在日志行里，因为轮询这个资源的人就是需要它的人。
一个报 FAILED 而无话可说的作业，是把它的客户端送去找运维。attempt 也留着：第四次尝试的作业和一个全新的
作业，少了这个数就长得一模一样。

重试是**显式命令**而不是自动重试，这是刻意的一半：一个因为 period 写错而失败的作业会永远以同样的方式失败，
自动重试把一次可见的失败变成一个看不见的循环。自动重试适用于"失败大概是暂时的且活很短"——那正好是库的
outbox 中继，也正好不是这里。

sample 提供的是**重试没有后果**：attempt 累加、上一次的产物被丢弃、进度被忘掉。所以运维盲目重试是安全的，
而这个性质才让"让人来决定"成为可行的策略而不是负担。

租约让被杀掉的 worker 不需要任何人发现它死了就能恢复：它什么都没释放（它做不到），所以认领只是到期，
`status = 'RUNNING' AND lease_until <= now` 这半个谓词把它捡回来。实测：租约有效期内别人拿不到；
时钟推进五分钟后拿得到，且 attempt 变 2。

## 12. 过程记录：两个自己的坑，都不是库的

写这一篇撞了两个，都值得写下来因为它们的症状都在别处：

1. **`ResultHandler` 的 mapper 方法必须显式给结果类型。** 方法返回 `void`，MyBatis 无从推断行类型，
   少了 `@ResultType` 会在**调用时**报"需要 result map"。是调用时而不是启动时——对一个导出端点来说，
   意味着第一个响应已经把 header 流出去了。第一轮 76 个用例里的多数失败都源于这一处。
2. **CGLIB 代理上的 `final` 方法会在未初始化的代理实例上执行。** `OwnTransaction` 带
   `@Transactional`，Spring 用 CGLIB 子类包它，而代理实例是**不跑构造器**创建的，所以它自己那份字段是 null。
   非 final 方法被覆写并委派给构造好的目标对象；`final` 的做不到，于是它在代理上跑，碰到第一个字段就
   `NullPointerException`。编译通过、上下文启动、第一次读崩掉。父类里因此一个 `final` 都不能有，
   `MyBatisProgressBoard.Base` 的 javadoc 里写了这条。
