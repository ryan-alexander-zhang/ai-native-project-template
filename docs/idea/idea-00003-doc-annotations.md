# 文内标注（Annotation）：选区上的提问与改进请求，攒一批统一提交

## 问题陈述

读文档时产生的反馈是**带位置的**——针对的是某一句话、某一段——但白板现有
的两条反馈通路都接不住这个位置：

- 答疑是整篇层面的：问题只能用散文自己描述位置（「第三节第二段那句……」），
  agent 拿到的是转述而不是选区本身；描述位置这件事本身就是摩擦。
- 改进型反馈（这句话错了/漏了/要连带改别处）目前没有通路，只有人工操作链：
  自己开修订轮把文档转 `draft`、自己改或发起共写、审计、接收——发现问题的
  人还得亲自当操作员，或者当场中断阅读去做这一串。
- 反馈只能逐条即时发起：读完一篇攒下的多个点，要么一个个发（每个答疑是
  独立线程），要么记在脑子里/别处等着丢失。阅读被反复打断，或者反馈被吞掉。

## 产品设想

在编辑器的编辑与预览两种视图态下，选中一段文本、右键添加一条**标注**；
标注锚定在选区内容上，类型二分——**question**（就这段有疑问，想要回答）与
**issue**（这段有问题，要求修改文档乃至相关文档）。一份文档可攒多条标注，
最后一键**统一提交**；提交后逐条可见进展——question 的回答、issue 引发的
修改。

### 1. 选区标注

- 编辑与预览两种视图态下均可：选中文本 → 右键 → 选类型、填内容。
- 一份文档可同时存在多条未提交标注；未提交前可改可删。
- 类型恰为两种：question 与 issue。（comment 类型在 idea 阶段已裁掉，
  见已定方向。）

### 2. 内容锚定

- 标注锚定**选区文本及其上下文**，不锚行号——文档其余部分变动时锚仍有效。
- 被锚定的文本本身被改掉或删掉时，标注成为**孤儿标注**（提交前后的处置
  见已定方向 9、10、13）。

### 3. 统一提交

- 一个按钮提交该文档全部未提交标注。
- question 走既有答疑机制：headless 只读问答，不改文件、不产生 commit；
  与答疑的差别只在问题自带选区锚定的原文与上下文。
- issue 启动 agent 会话走既有修订轮：文档转 `draft`，会话按标注逐条修订，
  之后审计、接收照既有语义走。

### 4. 进展追踪

- 提交后逐条可见状态：question 的回答内容，issue 的处理进展与所做修改。
- 呈现入口正名**标注列表**；与既有问题列表（答疑的第三视图态）并列一个
  新视图态还是合并呈现，属 design。

## 早期价值判断

- 把「读文档时发现的问题」从散文转述变成带精确位置的结构化反馈：agent 拿到
  的是原文选区而非二手描述，人省掉描述位置的摩擦。位置精度对评审场景
  （接收前的人工通读）价值最直接。
- 攒批提交把「读」与「反馈处理」解耦：阅读不被打断，会话也从 N 次发起变成
  一次批处理。
- issue 通路把「发现问题 → 修订轮」的人工操作链自动化：发现问题的人只负责
  指出问题，转 `draft`、修订、走流程由白板与 agent 承担。

## 已定方向

1. **类型二分**：只有 question 与 issue；comment 裁掉——「小补充」若值得
   动文档就是 issue，不值得就不必进系统。
2. **question 复用答疑**：只读、不改文件、不产生 commit；答疑的既有语义
   （`spec-00005`）原样适用，增量只在问题携带选区锚定。
3. **issue 走修订轮**：由提交时启动的 agent 会话执行，draft → 修订 →
   审计 → 接收，不另造第二条修改通路。
4. **锚内容不锚行号**：锚定选区文本与上下文，接受「锚文本本身被改」这一种
   失效形态并为它设计孤儿处置，换取对其余一切改动的稳健。
5. **不锁编辑**：现有设计里编辑器打开不锁文档（agent 外改经变更推送进白板，
   未保存改动靠保存冲突拒绝，`spec-00001-FR-42`/`FR-5`；共写更是 agent 在
   编辑器打开期间写入的既有先例）。本 idea 沿用该取向：不为标注引入
   「编辑期间禁止 agent 写入」的新锁，处理期间的呈现复用既有机制的问题
   属 design。
6. **会话形态**：同次提交的全部 issue 作为材料合入**一个共写会话**逐条
   处理（复用既有共写，不新立会话种类——`decision-00015` 立项时已否决
   「修订会话」路线，spec 轮审计揭出撞车后域主裁定复用；同文档互斥本也
   不允许多个，逐条修改共享上下文、收束一次 commit）；question 按既有
   语义各开答疑线程，不占用文档，总并发上限按既有答疑口径适用。
7. **连带范围**：会话只修订目标文档——由共写写域（`rule-00001-BR-30`
   收束过滤）保证，不是指令纪律；发现需要连带改关系文档时停下来（走
   既有等待输入机制）向域主报告，连带修改不在本会话落地，由人对关系
   文档另行处理。
8. **状态守门在入口**：issue 类型只对能合法转回 `draft`（或本就在
   `draft`/`open`）的文档开放；`resolved`/`archived` 的文档右键菜单里只有
   question。不让人攒一堆注定提交不了的标注。
9. **锚漂移提交时校验**：编辑期间不追踪锚；统一提交那一刻逐条重新定位，
   定位不到的标为孤儿标注。不做实时重锚。
10. **孤儿单条拦下**：提交时孤儿条目留在未提交区并标明失效，待重新选区或
    删除；其余条目照常提交，一条失效不卡整批。
11. **双模式都要**：编辑与预览均可标注；预览选区映射回 Markdown 源文本
    （用带位置信息的渲染器）作为 design 必解题。
12. **落盘板外**：标注与逐条进展落 `.whiteboard/` 不入 git，与答疑线程
    同口径；issue 引发的修改靠既有 commit 留痕。
13. **处理中锚失效不算失效**：标注提交时即携带选区原文引用，agent 处理与
    进展呈现以引用兜底；锚只服务于编辑器/预览里的定位，定位不到退化为
    「原文已变更」提示，不中断处理。
14. **命名**：总称**标注（Annotation）**、锚定机制**选区锚（Text
    Anchor）**、失效态**孤儿标注**、呈现入口**标注列表**——避开已被关系边
    占用的「锚点（Handle）」与已属答疑的「问题列表（Ask List）」；随本
    idea 接收写进 `CONTEXT.md`。
15. **不另攒痛点实录**：本地单人形态、域主即用户，使用直觉即一手证据，
    域主裁定直接进 PRD（有别于 `idea-00002` 先攒数据的做法）。
