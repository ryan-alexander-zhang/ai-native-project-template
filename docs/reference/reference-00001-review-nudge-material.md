## 2. Summary

草记提出：文档转入待评审后，负责人不在电脑前，文档就一直挂着，评审因此卡在
人身上。设想是给白板加「评审提醒」——文档进入待评审状态超过一定时间（举例
为半天），就往负责人手机推一条提醒，点开可直接看到文档正文并一键通过/驳回。

草记同时给出两组口头收集的等待时长数据，以及一条边界：只做提醒，不做移动端
编辑。数据为三轮评审的小样本、口头收集，非实录测量。

## 3. Excerpts

> 评审经常卡在人身上：文档转到待评审后，负责人不在电脑前就一直挂着。
> 想法是给白板加一个"评审提醒"：文档进入待评审状态超过一定时间（比如
> 半天），就往负责人的手机推一条提醒，点开能直接看到文档正文和一键
> 通过/驳回。

> 已知的痛点数据（口头收集）：
> - 最近三轮评审平均等待 26 小时，其中两次是负责人"忘了"。
> - 驳回后再提交的等待更长，平均 31 小时。

> 边界：只做提醒，不做移动端编辑。

## 4. Relevance

- 26 / 31 小时两个数字是 `idea-00002` 问题陈述的唯一证据来源；样本为三轮、
  口头收集，引用时须带上这个强度。
- 草记的用词与本体系术语不对齐，需在 idea 正文中翻译后使用：「待评审状态」
  在本体系是 `draft`；「通过」是接收；「驳回」在本体系无对应动作，最近的是
  澄清（`CONTEXT.md` 明列 _Avoid_：打回、驳回）。
- 「往手机推」触及 `decision-00010` 已否决的送达路线（B：SW + Web Push；
  D：服务端直发），该否决的前提是本地单人形态；本材料不构成推翻它的理由，
  只提出了重新裁定的动机。
- 「只做提醒，不做移动端编辑」与同一段的「一键通过/驳回」在草记内部即不自洽，
  按输入原样留证，裁定归 idea 的 Open Questions。
